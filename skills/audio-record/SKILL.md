# 录音 → 原始转录 + 最终记录

处理任何录音，都交付：

1. **原始转录**（md）：`[时间戳] 说话人：文字`。保持录音原貌，由规则去掉"嗯、呃"、乱码和口吃重复，**不订正错别字，不改数字**。转写一出来就发，用户不用等校订。
2. **最终记录**（PDF）：校订后的版本，正文是 `说话人：文字`。错别字、乱句、说话人归错、被切断的一段话都由 `proofread` 工具校订，你不用自己逐句改。公司、地址、人名、时间、数字用底色标出，文末有"涉及公司"表。
3. **一段给用户的说明**：做了什么、哪几处请确认。由代码生成（`message`），你照着转述，不要自己另写。
4. **修改清单**（md，可选）：是否随结果发出由 `skills/audio-record/scripts/config.yaml` 的 `emit_change_list` 控制，线上默认不发，开发调试时发。最后的回答会提醒用户可以回复"要修改清单"；用户问"你改了哪些地方"或"要修改清单"才生成给他（见"第三步"）。

另外会存一份**修订单**（json），是之后修订的依据：用 `write_file` 保存但**不交付**。

用户只说"转录"也是这几样。用户明确只要其中一样（"只要文字稿"）才少给。不用另外加载 asr-correction，整条流程都在这里。

## 第一步：选场景，没有信息才问一次，再读文件

场景决定最终 PDF 的名称、封面的信息项和保密声明，在 `config.yaml` 的 `scenarios` 里配（现有：访谈、会议、其他录音；要加新场景在那里加一段）。按用户的说法、文件名、对话上下文选一个；实在判断不了就选"其他录音"。

**读录音之前**，先看用户给过什么：对话里说过的（日期、人员、说话人数）、一并上传的信息文件、人员名单，都算。**给过任何一种就不问**，先读信息文件，直接往下走，缺的项就不写。**一点信息都没给过**，才用 `ask_user` 问一次，只问一次。这是**邀请补充**，不是逐项索要：问"有没有相关信息可以补充，比如访谈日期、参与人员的姓名和职位、录音里有几个人说话，没有的话我就直接开始"，不要写成必填清单。场景 `fields` 里的各项只是可以举的例子；用户给了别的信息（地点等），照样原样放进 `info`，会写进封面。

访谈场景的 `info` 里，访谈日期、访谈类型写在封面的标签行；**访谈人员、受访人员分开写**，在封面下方成表，每人写成"姓名-职位-公司"，没有的那一项不拼（没有职位就是"姓名-公司"）。访谈人员多位用顿号隔开；受访人员多位用换行符 `\n` 隔开，每人一行。受访人都来自同一家公司时也每人写全，不省略公司。

用户可以用文字、语音或文件回答，给什么用什么；回答"没有""不知道"，就不写那一项，说话人写成"说话人1""说话人2"。**问过一次就不再追问**。

**自动推断说话人数**：`read_file` 读录音时传 `speaker_count`，来源只能是已知信息：用户给的人员名单人数、用户明说的人数、用户上传的材料里写明的参与人数。有依据就传，没有依据就不传，让厂商自己判，**不要凭"一般访谈是两个人"这类猜测去传**。读完发现 S 标签数和已知人数对不上，在回答里告诉用户，不要悄悄重读（重读会重新转写、重新花钱）。

说话人对应关系只用用户给的（资料里写明的访谈人、访谈对象），不自己推断身份。**封面的人员表和说话人名字的姓名、职位保持一致**。说话人名字（`speakers`）写"张三（投资经理）"，不带公司。

## 第二步：读、出原始转录、校订、出最终记录

**中间不要写文字**：没有工具调用的一段文字会被当成最终回答，流程就此结束，写不完还会被截断。每一步直接调工具，不预告下一步，不写分析。

0. 开始读录音之前（问过信息的话，在问完之后），先调一次 `notify_user`，两三句话告诉用户：收到了录音和资料，识别为什么场景、说话人怎么对应，会先发原始转录，再发最终记录，大约几分钟。每次处理只调这一次。
1. `read_file` 读完整份转写（每页都读），了解谁在说什么、谈哪家公司。背景材料也读。
2. `export_transcript` 得到转写稿 file_id。
3. **原始转录，马上发，同时准备校订的输入**。`run_python`（`file_ids` 带上转写稿）：

```python
import sys
for p in ("skills/asr-correction", "skills/report", "skills/audio-record"):
    sys.path.insert(0, p)
from eva_record import prepare

out = prepare("inputs/<转写稿 file_id>/xxx_转写稿.json",   # 路径见 run_python 返回的 inputs；文件只有通过 run_python 的 file_ids 才会进工作目录，没带就找不到
              {"S1": "张三（投资经理）", "S2": "段静（财务负责人）"}, "段静_财务负责人.mp3")
print(out)
```

   `write_file` 保存 `out["raw"]`，`deliver_file`（`immediately=true`，`inline_if_short=true`）发出去，中间不写文字。再 `write_file` 保存 `out["proofread_input"]`，得到校订输入的 file_id（只保存，不交付）。

4. **收集线索，然后校订**。线索是你已经掌握的、帮助改对名字的信息，写成一段文字交给 `proofread` 的 `hints`：
   - 用户材料里写明的人名、公司名（含全称）；
   - `search_hotwords` 命中的写法（上市公司和行业术语；热词表没有的不代表错）；
   - 本租户确认过的写法；
   - 联网查到的公司全称，按"公司名怎么处理"第 4 条的门槛标"已核实（联网）"或"未核实"。

   没有线索就不写 `hints`。然后调 `proofread`（`file_id` 是校订输入的 file_id），得到校订结果的 file_id。**校订的判断由这个工具做，你不要自己重写稿子。**

5. `finish`（`run_python`，`file_ids` 带上转写稿和校订结果）：

```python
import sys
for p in ("skills/asr-correction", "skills/report", "skills/audio-record"):
    sys.path.insert(0, p)
from eva_record import finish

out = finish(
    "inputs/<转写稿 file_id>/xxx_转写稿.json",
    corrected="inputs/<校订结果 file_id>/xxx_校订.json",     # 重做过的块有第二个结果文件，就写成列表，后面的覆盖前面的
    speakers={"S1": "张三（投资经理）", "S2": "段静（财务负责人）"},
    scenario="访谈", info={"访谈日期": "2026-07-07", "访谈类型": "尽调访谈", "访谈人员": "张三-投资经理-某投资公司", "受访人员": "段静-财务负责人-某科技公司"},
    source="段静_财务负责人.mp3", materials=["段静访谈信息.md"],
    companies=[{"spoken": ["聚子化学"], "name": "广东聚石化学股份有限公司", "basis": "上市公司，热词表", "status": "已确认"}],
)
print(out["record"], out["state"], out["changes"])
print(out["message"]); print(out["refused"])
```

   标色的实体（公司、地址、人名）默认取校订结果里的；你知道还有没标上的，用 `entities=[("公司", "聚石化学")]` 补充。`out["refused"]` 不为空，是有的块没通过检查（改得太多、缩成了摘要）或没拿到结果：用 `proofread` 的 `redo` 只重做那几块，`reason` 照抄 `refused` 里的原因，再重跑一次 `finish`（`corrected` 写成两个结果文件的列表），只重做一次。

6. `finish` 一返回，**下一步就是 `write_file`，中间不要写任何文字**。`run_python` 返回的 files 里有路径。依次：
   - 修改清单（`out["changes"]` 不是 None 时，即开发配置）：`write_file` 后 `deliver_file`（`immediately=true`）。
   - 最终记录 PDF：`write_file` 后 `deliver_file`（不带 `immediately`），随最后的回答一起发出。
   - 修订单（json）：只 `write_file`，不交付。**必须保存**：之后的修订都靠它重放，没存就只能整份重做。
7. **最后的回答就是 `out["message"]`**，原样给用户：回答的第一个字就是 message 的第一个字，最后一个字就是 message 的最后一个字，前后不加任何话（"现在输出""最终记录已排队""按 skill 要求"之类都不行），不要用代码框，更不要出现 finish、message、skill 这些词。回答里只有那段话本身。不要把原始转录或记录的正文再贴进回答，也不要提内部的东西（工具、脚本、文件编号、"闸门"、"被拒"）。

`finish` 报错时按报错说的改参数再重跑；**不要绕过它自己手写 md 或 PDF**，文件名、行格式、标色都由它保证。`skipped_marks`（没标上的）和 `unmarked_hints`（看着像公司名却没标的）不为空时，补好 `entities`（只写要补的，原来标的保留）后调一次 `revise(out["state"], {}, entities=[("公司", "聚石化学")])` 重新生成 PDF，只重跑一次，PDF 以最后一次为准。

## 公司名怎么处理

公司名是用户最在意的部分，也是最容易错的。证据从强到弱：

1. 用户给的材料里有这个名字（信息文件、之前的对话）：写进线索，校订按它改。
2. 本租户以前确认过的写法（`search_hotwords` 返回 `source` 为 `tenant`）：同上。
3. 热词表里读音高度吻合的上市公司（`聚子化学`→`聚石化学`）：同上。
4. 非上市公司、热词表没有的名字：先用 `web_search` 查全称，**每条录音最多查 10 次**，只查本地没有、又确实影响理解的名字，查询里带上能区分的信息（地名、行业、上下游）。网页结果可能互相矛盾，要交叉看。**几乎可以确认才算有依据**：查到的工商登记全称和录音里的叫法读音对得上，并且至少有一条能区分的信息吻合（地名、行业、上下游、股东或集团关系、用户材料里提过的），多条结果指向同一家。
   - 达到门槛：线索里标"已核实（联网）"，校订可以据此改正文里写错的字（口述的简称仍保持简称）；`companies` 里 `basis` 写出吻合的那条信息，状态"已确认"。
   - 没达到（只有名字像、有多个候选、结果互相矛盾，或查满 10 次仍定不了）：线索里标"未核实"，不据此改正文；`companies` 状态"待确认"，会变成请用户确认的问题。
   错的全称会直接进正文，所以宁可标"待确认"，也不要把"像"当"几乎可以确认"。
   - 用户材料写明了受访人所在的公司（访谈信息里的公司全称），录音里同一个字头的叫法（`湖北巨石`对`湖北聚石新材料科技有限公司`）按它改；同一家公司的兄弟公司、关联方不在此列，没有依据不改。
   - `resolve_entity` 是企查查，**走企查查的一次 0.1 元，每条录音最多 4 次**，命中本地主数据的不收费、不计次。要查的公司在同一步里一起调用，不要一家一步。公司对齐不用 `query_company`（对外投资等维度另收费）。只对已经有全称的公司用（材料、热词表、`web_search` 给出的全称），用来取法人和统一社会信用代码；**不要拿录音里的口语叫法直接去查**，口语叫法查出来的多是不相干的候选（"巨石供应链"会查成另一个城市的公司）。返回的 `name_match` 是 `none` 就是对错了，不采用。对上了，`companies` 那一行带上 `legal`（法人）和 `uscc`（信用代码），PDF 里会写成"全称-法人-信用代码"。
5. 同一家公司在录音里有几种写法（`聚石`、`巨石`、`聚鑫`），或者想把一个名字换成读音一样的另一个字：必须有上面 1 到 3 的依据才能改正文。宁可不改也不要把对的改错：同一个录音里，不同的公司可以只差一个字（`湖北巨石`和`聚石环境`就是两家）。系统会自动把读音一样、写法不同的名字列给用户确认。

正文里**口述的简称保持口述的样子**，不写成全称。银行、农商行等金融机构也是公司，口述的"建设银行""农行""江陵农商行"同样要对齐到全称（大型银行在 `resolve_entity` 的本地主数据里，命中不花钱）。校订结果里每个标成公司的实体，`companies` 里都要有一行，会出现在 PDF 文末的"涉及公司"表：每行 `{"spoken": 口述写法列表, "name": 工商登记全称, "basis": 依据（用户材料/租户确认/热词表/联网检索），"status": "已确认"或"待确认", "legal": 法人（可选）, "uscc": 信用代码（可选）}`。**核对过的都要列**，不论最后改了正文、没改、还是拿不准：`basis` 用一句话写清楚做了什么、为什么（例如"材料写明受访公司，正文 湖北巨石→湖北聚石"、"联网只有名字像，正文没改"）。`spoken` 只写录音里听到的叫法；查不到全称的公司也列一行，`name` 照写口述的叫法，状态"待确认"，`basis` 写没查到的原因，用户会被问"知道全称的话请告诉我"。依据不够硬的标"待确认"，会变成请用户确认的问题。`basis` 是写给用户看的一句人话，不要出现工具名和字段名（`resolve_entity`、`web_search` 等），写了会报错。**依据只写这次真的做过的事**：没调过 `web_search` 就不能写联网检索；全称是凭记忆想出来的，没有材料、热词表、本地主数据或联网结果支撑，状态一律“待确认”。请用户确认的问题里出现的写法，对应的行也必须是“待确认”，不要表里写已确认、问题里又在问。联网查到的按第 4 条的门槛判断，标"已确认"就要在 `basis` 里写出吻合的区分信息，用户在 PDF 的"涉及公司"表里能看到这一栏。

## 第三步：用户看了之后要改

用户说"把 X 改成 Y""X 是 Y 公司""A 和 B 是同一家，写 A""应用 c3"，或回答了请确认的问题时，**不要从头重做**，用修订单重放。修订单（上一轮 `write_file` 返回的 file_id）放进 `run_python` 的 `file_ids`，路径见返回的 inputs。找不到修订单（上一轮没保存，或会话里没有）就如实告诉用户这份记录需要重新整理一遍，问他要不要，**不要硬凑**。

```python
import sys
for p in ("skills/asr-correction", "skills/report", "skills/audio-record"):
    sys.path.insert(0, p)
from eva_record import revise, change_list

state = "inputs/<修订单 file_id>/xxx-修订单-时间戳.json"
# 口述"把聚石供应链改成巨石供应链"：用户一般不说块号，就不写 block，每一处都会改（拆块之后的文字也能找到）
out = revise(state, {"add": [{"old": "聚石供应链", "new": "巨石供应链"}]})
# "X 是 Y 公司"：改正文里的写法（需要的话），同时更新涉及公司表；companies 给的是完整的新表，不是增量
out = revise(state, {"add": [{"old": "巨石环境", "new": "聚石环境"}]},
             companies=[{"spoken": ["湖北巨石"], "name": "湖北巨石新能源科技有限公司", "basis": "用户确认", "status": "已确认"}])
# "应用 c3、c5，不要 c7" / "全部应用"（把待确认的都改了）：
out = revise(state, {"apply": ["c3", "c5"], "skip": ["c7"]})   # 或 {"apply": "all"}
print(out["message"], out["failed"])
```

- 修订只出新的 PDF 和修订单（`out["raw"]`、`out["changes"]` 是 None），文件名是新时间戳，旧的不覆盖。**只 `write_file` 保存并交付 PDF**，修订单保存不交付；不要重发原始转录。回答就是 `out["message"]`。
- 用户**明确说出**了某个名字的正确写法（"湖北巨石就是湖北巨石新能源科技有限公司"），改完后用 `confirm_term` 记下：`term` 是正确写法，`heard_as` 是被听成的写法，`kind` 是 `company`。这是下一次自动改对的依据，只有用户说了才记，你自己推断的不记。
- 用户问"你改了哪些地方"或说"要修改清单"：`change_list(state)` 生成对照清单，`write_file` 后 `deliver_file`。清单里已应用的行改成"不应用"就撤回，用户发回来用 `parse_change_list`。
- 用户说"把 X 标成公司（地址、人名）色"：`revise(state, {}, entities=[("公司", "X")])`，类型只有 公司、地址、人名（金额、日期、数字系统自动标）；X 必须和记录里的文字一字不差，在 `skipped_marks` 里看到找不到，就如实告诉用户。只 `write_file` 保存并交付新的 PDF。
- 用户的话和修订单对不上、改不动的，如实告诉用户哪一处没改成、原因，不要假装改了。
- 用户把修改清单改了发回来：`parse_change_list(清单文字, state)` 得到 decisions，再 `revise(state, decisions)`。

## 规则

- 原始转录和最终记录的**事实内容**以录音为准：不总结、不概括、不补写。用户口述与事实不符也照录。
- 数字（金额、年份、比例）不自己改。只有语音识别把数字念重了的明显错误（`202025年9月`、`700700万`）才改，通过的会在 PDF 里自动带角标，文末"数字变更说明"逐条写原数字→新数字。其余存疑的数字保持原样。
- 标色只标正文里确实出现的实体：公司名（含口述简称）、地址、人名，金额、比例、数量、日期会自动标。"政府""补贴""高新技术企业"这类普通名词不是公司名，"土地款返还"这类词不是数字，拿不准是不是就不标。
- 开始读录音之后不再向用户提问，信息只在第一步问一次。问选择题时给带编号的选项；用户的回答对不上任何选项，选最接近的那个，并说明"按××处理"，不要再追问。
- 引用录音内容时，摘抄取自 `read_file` 返回的原始转写块，不取校订稿。
