## 1 数据飞轮的公共层设计
- 第一版不回灌联网搜索数据（已定，见架构设计第 6 节）。
- 公共别名（`company_aliases`）怎么随使用增长：候选做法是多个互不相关的租户各自确认了同一个称呼指向同一家公司后，经单独校验的入口提升到公共层；门槛（几个租户、是否人工复核）、防协同投毒、和架构设计「租户自己确认的别名不进公共表」的关系都没定。
- 之后的积累路径、存储模型、检索方式、更新与去重，后置到核心循环跑通后单独设计。

## 2 用户说的到底是哪家公司：对话上下文与实体活动记忆
- 现状：`tenant_aliases` 只记"用户把某个称呼确认成某家公司"，每个称呼要用户确认过一次才有。同一会话里模型靠 transcript 里先前的 `resolve_entity` 返回记得。
- 想法（还没设计）：记录每个租户最近在聊哪些公司（实体的活动期）和相关人员（人员的活动），用来判断"阿里""他们"指谁，也支撑穿透时顺着人和公司往下走。
- 要先想清楚的：怎么避免把模型自动选的、用户没确认的当成确认（自动选错了会一直错）；活动期的衰减和范围（会话内、租户内、跨会话）；人员属于隐私，只能是租户私有，不进公共层（架构设计第 6 节）；这份记忆是工具查询还是进上下文；和 `tenant_aliases`、压缩摘要的关系。
- 用户明确要求记住的偏好和纠正已经有了：`tenant_memories`（见 `新表设计.md`），不含这里说的实体活动记忆。

## 3 skill 的自进化：从重复流程沉淀、修正、按需拆分
- 目标：反复出现的流程固化成 skill，已有 skill 被纠正后自我修正，正文长到适合拆时拆出 `references/`。不预设固定的拆分规则，由维护 agent 判断。参考 `reference/hermes-agent` 的后台复盘与 curator（索引见 CLAUDE.md），只借鉴形状。
- 已确认的方向：
  - skill 分两层：租户私有层（只对该租户生效），和候选队列（经用户审核后升入公共层）。两层都要。公共层的升入口单独校验，不能绕过（硬约束第 5 条）。
  - 第一版只出补丁提案，由用户批准后生效，不自动生效。等指标和回滚跑通再讨论放开。
  - 触发要跨会话：从会话日志里挖重复出现的流程。"重复"的次数阈值设得偏高，因为是多用户，一两个租户的习惯不该变成公共流程。阈值走配置。
  - 拆分只给"正文接近 `max_body_bytes`"这个信号，拆不拆、怎么拆由维护 agent 判断，阈值走配置，代码里不写拆分规则。
  - 只改 `SKILL.md` 和 `references/`，不改 `scripts/`（脚本会在沙箱里执行）。沙箱工作目录里的脚本副本每次运行都从 skill 快照重写，模型改了不保留，不做只读挂载（local 后端做不到，收益只是把静默白改变成当场报错）。
- 需要一个单独配置的维护 agent：与对话 agent 同一个循环，经同一个调用层记账，但系统提示、工具白名单、触发方式都不同；触发是离线的，不挂在用户的对话上。
- 还没定：
  - 轨迹存储：会话日志现在够不够做跨会话的重复挖掘，要不要单独的轨迹表。
  - 重复的判定：按工具调用序列、按用户意图、还是让模型归并；多少次、跨几个租户算"重复"。
  - 租户层 skill 存哪：存储层的哪张表或对象存储路径，怎么热加载；现在 skill 启动时全部校验，任何一个不合格都让服务起不来，运行时写入需要改成在写入口拒绝。
  - 提案的形态和审核入口：补丁格式、用户在哪里看和批准、被拒绝的提案是否记录以免反复提。
  - 版本与回滚：每次改动留版本；改前改后用轨迹指标（轮数、成本、来源覆盖、一次答对率）比较，变差能回退。
  - 租户数据防泄漏：从租户对话学出的内容进候选队列前，怎么剔除公司名、人名和具体事实。
  - 提示注入：维护 agent 读到的录音转写、网页、文件内容是不可信数据，学习信号只取自用户消息和轨迹形状，还是另有办法。
  - 预算：维护 agent 的模型调用算平台成本还是租户成本，触发频率和单次上限。
  - 使用统计：记录每个 skill 被加载的次数和最近时间，旁路存放，不写进 `SKILL.md`；用于判断闲置和归档。
- 碰到时先问用户，不自己猜（可用 `/grill-me`）。

## 4 网页渠道
方向和接口形状已定，见 `网页渠道设计.md`。下面几项还没定：
- 同一租户的多个会话能否并行在途：倾向同一租户一次一个（后端加锁最简单），但 `架构设计.md` 7.9 只写了"一个会话同一时刻只有一次在途运行"，租户级限制比它更严。
- 登录和租户来源：第一版固定一个网页身份并只监听 `127.0.0.1`，对外开放前的账号体系（手机号、SSO、企业账号）和计费、公共层隔离相关，没定。网页身份解析到租户的方式和与企微账号的绑定见 `架构设计.md` 第 6 节「租户与身份分开」；绑定令牌表、`enter_session` 事件处理、真正的账号合并（两边都有数据时搬数据、搬对象存储路径、处理文件重名和哈希冲突）都等做网页时再设计，企微客服链接带场景值的接口要先核对文档。
- 会话标题：第一版取首条用户消息前若干字；让模型生成标题要多一次调用和一处记账，是否值得没定。

## 5 企微菜单点击算不算用户主动发消息
- 企微发送文档只说"用户发送消息"开启 48 小时窗口和 5 条配额，没提点击菜单；接收文档把点击后的回复列为客户回复（`origin` 为 3）；名片消息的条件里明写"点击菜单消息不算"。没有任何一处说明点击会不会刷新窗口和配额。
- 现状：适配器按"点击不刷新"处理。带 `menu_id` 的消息不更新本地的窗口起点和已发条数，取消点击也一样。点击实际能刷新时只是少发，用户回复 1 就能继续；不会出现本地以为有额度、平台却拒收。
- 待验证（需要测试客服号）：用户发一条消息，机器人发 4 条文字加 1 条菜单用满 5 条，用户点击菜单，机器人再发 1 条。成功说明点击刷新配额，被平台拒收说明不刷新。
- 验证后要定的：刷新，就恢复点击重置本地计数，历史报告可以做成"点一个发一个"的菜单；不刷新，选择改走用户输入编号，菜单只做展示。
- 选项菜单（`ask_user` 的 `options`）已经按"点击不刷新"做好，不依赖验证结果；验证后只影响要不要恢复点击重置本地计数。

## 6 联网搜索和企业数据的结果怎么沉淀进公共层
- `web_results`、`qcc_results`、`qcc_queries` 现在是租户私有表，按会话存模型实际看到的内容和查询留痕。`qcc_cache` 是公共缓存，`web_results` 没有对应的公共缓存，是联网搜索结果唯一的一份，再查要重新付费。
- 想法：去掉租户和会话信息后升到公共层，走单独校验的写入口（硬约束第 5 条）。要定：搜索词和"哪个租户查过什么"属于私有，不能带出；`qcc_results` 里不在 `company_master` 的公司没进过 `qcc_cache`，怎么处理；旧快照与缓存新数据冲突时以谁为准；新鲜期怎么判。
- 在定下来之前，这三张表保留，不随租户数据清空。

## 7 用户要求删除自己的数据
- 现状：`context_reset`（用户说"新话题""清空聊天"）只让模型不再看到旧内容，日志（`transcript_events`、`channel_messages`）、对象存储里的文件和报告、租户术语写法（`tenant_terms`）、公司别名（`tenant_aliases`）、租户记忆（`tenant_memories`）都原样保留。模型被要求只说"之前的内容不会再用于对话"，不得声称已删除。
- 没有定：
  - 要不要提供"删除我的数据"，范围是日志、文件、报告、术语、别名、记忆中的哪些，对账本和审计记录怎么处理（计费要保留）。
  - 术语写法和别名目前只有确认入口，没有清除入口；是否加，由谁触发（用户说话，还是单独的管理入口）。
  - 日志只追加、没有 DELETE（`新表设计.md`），真删除要不要破例，还是用脱敏或到期归档代替。
  - 用户说"清空记忆"含糊时，模型用 `ask_user` 给选项（只清对话、只清偏好、都清），选项之外的清除能力以这一项的结论为准。
