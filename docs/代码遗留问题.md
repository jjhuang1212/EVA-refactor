# 代码遗留问题

> 已知但暂未实现的事项，以及占位处的接口形态。做完一项就删除该项。

## 1 文件读取与对象存储
- `read_file` 读纯文本（`text_extensions`，行号锚点）和 docx/doc/xlsx/xls/pptx/ppt/pdf/md/png/jpg（解析成块，块号加页、表、sheet 行区间、章节等锚点）。扫描 PDF 页和图片文件在解析沙箱里 OCR（tesseract，kind=ocr，锚点带 confidence，docx/pptx/pdf 里的嵌入图按位置 OCR 成块；一份文件共用 `ocr_max_images` 张额度，超出的、读不了的、识别不出文字的、小于 `ocr_min_image_pixels` 的图都在警告里给出位置或张数）。录音（mp3、m4a、wav、amr 等）经解析沙箱里的 ffmpeg 转成标准 wav 后转写，块带时间段锚点，细节见第 1 节末尾的录音条目。
- 解析镜像 `eva-parse:latest`（`sandbox_image/parse/build.sh`）已在服务器上构建（800MB），在 runsc（gVisor）下冒烟过：内置 ffmpeg 解 amr、mp3 正常，soffice 25.2 和 tesseract（chi_sim、eng）能启动。**还没在镜像里跑过真实的 doc/xls/ppt 转换和 OCR**；老式 doc/xls/ppt 经 soffice 转换只在开发机（LibreOffice 26.8）用真实文件验证过。解析器只认 `PATH` 里的 `soffice`，不读 `LIBREOFFICE_PATH`；本地沙箱后端只传白名单环境变量，开发机要把 soffice 目录加进 `PATH`，否则 `test_parsing.py` 里的转换用例会跳过。
- 解析缓存键含解析器源码哈希，镜像里库的版本不在其中：升级镜像里的解析库后，要手动换缓存（改 `limits` 里任一上限，或清 `parsed/` 前缀）。
- 解析结果没有负缓存：损坏的文件每次读取都会重新进沙箱解析一次。
- docx 读正文、表格、嵌套表格、文本框、脚注、尾注，不读页眉页脚和批注；图片只计数提示。pptx 不读图片；xlsx 不读图片、图表、合并单元格范围和批注（只读模式拿不到）；pdf 有文字的页里嵌的图片只在警告里列出页码。
- OCR 只在本机用 tesseract 5.5 验证过，`eva-parse` 镜像（Debian 的 tesseract 5.3）只确认了语言包在，没跑过识别；`ocr_max_images` 乘单张耗时要小于解析沙箱时限，服务器上的单页耗时没测。
- 嵌入图片 OCR 只认印刷体文字。文档里的内嵌图不论 OCR 读没读出字都交视觉模型（OCR 文字单独成块在前），所以流程图的连线和层次有描述；上传的图片和扫描页仍是读出字就只给 OCR，要看关系用 `view_image` 追问。xlsx 内嵌图片（只读模式看不到）、页眉页脚里的图、pdf 铺满整页的扫描底图（按文字层读）没有 OCR。emf/wmf/svg 打不开，会在 `images_unreadable` 警告里列出。
- 图片看图：`view_image` 经调用层让 `vision` 模型（`qwen3.8-flash`）回答模型提的问题，已用真实接口验证。`image_token_bound`（预扣时一张图的 token 上界，4096）按真实用量定：线上 `qwen3.8-flash` 对大图服务端缩放，用量封顶在 2565 token（实测 3000×2000 和 6000×4000 相同）；换视觉模型要重测；没有缩图，超过 `view_image.max_file_bytes` 的图直接拒绝；只收 png、jpg；docx/pptx/pdf 里的嵌入图不走 view_image，只有解析时的看图描述。`view_image` 的结果没有缓存，同一张图同一问题重复问会重复付费。
- 解析时看图：`vision_max_images`（每份文件 10 张，必须小于沙箱 `max_files`）、`vision_blank_stddev`（空白图判定）、`vision_max_image_bytes`（超过按比例缩小）在 `parsing.yaml` 的 `limits`，改动会让解析缓存失效；并发和输出上限在 `vision` 小节。本机 LocalSandbox 加真实 `qwen3.8-flash` 验证过占位、补全、图级缓存、整份缓存和失败重试，服务器 docker 后端（gVisor、`eva-parse` 镜像）验证过 `.png` 与 `vision/` 子目录产物放行、OCR 与占位块分流（4 张小图沙箱阶段 1.5 秒）；**没测**真实扫描件多图的 OCR 耗时，也没在服务器上跑带数据库和 MinIO 的完整 `load_parsed`。解析结果总是带占位块缓存，占位图按内容哈希存进对象存储、sha256 记在 `parsed.json` 的 `images`；看图是读取时的第二步，看失败只重问失败的图，不重跑沙箱，但持续失败（尤其接口超时）时每翻一页都会重问一轮，前后页的描述来源可能不同（块数不变，游标不错位）。文档内嵌图的追问用 `view_image(file_id, question, block)`，图从这里读。每次读取有图的文档要查每张图的描述缓存，图多时可考虑把描述也记进 `parsed.json`。描述长度超过 `block_max_chars` 会被截断并记 `vision_truncated`。
- 录音转写：短录音（不超过 `asr.yaml` 的 `max_seconds`，含企微语音）走同步接口，长录音走异步 filetrans（`eva/model/filetrans.py`，说话人分离），超过 `long.part_max_seconds` 的在宿主按停顿切段、带重叠区，`eva/tools/speakers.py` 用重叠区对齐各段说话人并去重；对不上的说话人保留成 `p2.S3` 并在 warnings 里列出。结果按（租户，内容哈希，版本）缓存，空结果不缓存。`read_file` 可传 `speaker_count`（2 到 `asr.long.speaker_count_max`），只在走分说话人的长录音转写时用得上，用不上时 warnings 里有 `speaker_count_ignored`；人数进缓存版本，各人数各存一份，「最近一次解析」指向刚读的那份。厂商对 `speaker_count` 的实际行为（是硬约束还是参考值）没连真实 DashScope 验证。**都只用假厂商测过，没连真实的 DashScope 调过**：同步接口的应答形状来自旧项目和文档，filetrans 的上传、提交、轮询、结果形状来自旧项目代码，真实调用时可能有出入。已知缺口：轮询超时、结果下载失败时任务已受理、可能已计费，错误详情和日志里有 `task_id`，但没有把 task_id 持久化，用户重试会重新提交再付一次钱；要解决需要记下"文件 → 进行中的任务"并在重试时续轮询。长录音转写在 `read_file` 里同步等完（最长 `poll_max_wait_seconds`），期间占着该租户的会话 worker。预处理会话沙箱时限 300 秒，4 小时录音的解码耗时没测。
- 转写纠错：`search_hotwords`（`eva/tools/search_hotwords.py`，只查公共热词表，按拼音窗口匹配，不碰租户数据）、`export_transcript`（转写稿存成 json 供 `run_python` 用）和 `asr-correction` skill（改动清单加 `diff_gate` 闸门，口语整理成稿是同一份清单里 `kind=tidy` 的改动，用户要求才做）。热词表里的行业术语权重、公司别名没有参与匹配；拼音匹配对多音字取 pypinyin 的默认读音。只用假数据测过，没有让真实模型走一遍纠错流程看轨迹指标（轮数、成本、改对率）。`eva-sandbox` 镜像加了 pypinyin，已重建。
- 转写纠错的记忆：`confirm_term`（`eva/tools/confirm_term.py`，表 `tenant_terms`，迁移 0005）记下用户确认过的写法和常被听成的错写，`search_hotwords` 先查本租户再查公共表。**写入只靠 skill 约束，没有 hook**：skill 要求用户明确答复后才调用，但代码上不拦，模型可以不问就写。发现乱写再加 hook（写入前要求最近几步内有用户消息）。租户表每次现查不缓存，条数上限 2000（配置）。`remove` 只能按完整写法删，没有列出全部已确认写法给用户核对的入口。
- **转写时带背景（`input.context`）没做**：旧项目实测，成对消息形态的背景能把基线必错的专名救回 3/3，换成诱饵词也 3/3 被带偏，所以背景只能来自用户明确给的或 `tenant_terms`。形状限制：最多 5 轮、每轮 user+assistant 合计不超过 400 字符，纯字符串会 `InvalidParameter.ParseError`。要先用真实 DashScope 验证现有的同步、异步请求形状，再往上加。
- **长稿纠错的上下文成本没测**：纠错在会话里由主模型做，读完整份稿子会让上下文增长、每一步都重发。没有真实数据前不做批处理；要做时优先考虑子 agent 或工具内部按块分批，接口不变。旧项目的教训：单次输出（含思考）才是瓶颈，不是上下文，15 万字稿的改动清单装不下任何输出上限，所以改动清单要能按块分批提交给闸门（现在的 `apply_changes` 每次调用独立，可以分批，但批与批之间要靠 `save` 出的 json 接力，skill 里没写这个用法）。
- 纠错质量没有轨迹指标：没跑过真实模型，不知道主模型（`qwen-plus`）对音近词和专名的判断力，也不知道轮数、成本、改对率。第一次真实录音跑完后看这几个数再决定要不要换模型或拆成专用调用。
- `diff_gate` 的数字闸会误挡含数字字的专名（万科→万达、亿纬锂能这类名字里的"万""亿"），这类改动只能走用户确认。语气词、口语整理的"新出现人名"闸（旧项目有）没做，整理只靠字符来源比例防添词。
- 企微图片消息已接（jpg/jpeg/png，无文件名时按 Content-Type 兜底命名）。超过 20MB 的文件，企微投递的是内容只有文件名的文本消息（用户确认），渠道按"整条文本是单个文件名且扩展名在 `file_extensions` 里"识别并回复含大小限制（`file_limit_mb`、`image_limit_mb`）的重发提示；用户真的只发了一个文件名也会被这样处理，无法区分。**图片（2MB）、语音（2MB）、视频（10MB）超限时企微投递什么还不知道**，需要实测：图片目前按"下载回来不是 jpg/png 就回复重发提示"处理，是否也退化成文件名文本未知；语音已接收，下载回来的 Content-Type 是 `text/*` 时按超限处理，这个假设没实测；视频还没接收。
- 引用校验（页码存在、原文片段能在该页找到）要等有报告结构的流程，才有地方挂 hook；目前没有默认 hook。
- 溢出对象没有生命周期清理，也没有按会话回收。
- 上传大小等渠道数字由各渠道适配器自己定；console 的 `/upload` 不设上限，读取侧由 `max_file_bytes` 兜底。
- 联网搜索等产出大结果的工具出现后，再评估溢出阈值和预览长度是否合适。
## 2 模型调用层
- 流空闲超时：调用为非流式，没有。改流式时一并做。
- 熔断只按连续失败次数，没有错误率阈值。
- deepseek-flash 的高峰时段规则（`peak`）不排除中国法定节假日：节假日里的工作日按高峰价记，只会多算；补调休上班的周末则按空闲价记，会少算。要精确对账时加节假日表。
- 只计隐式缓存命中价。qwen 的显式缓存（创建价、命中价另算）没有支持，开启显式缓存前要先扩展 `cache_hit_path` 和计费项。
- 没有查询"今日剩余预算"的接口，只有 `Ledger.committed_today()`（已用加占用）和 `committed(session_id)`；告知用户或模型预算余量时再加。
- 预算只有租户按天一层。架构设计里长任务"每次 ¥20"的单次上限没有实现，`start_task` 做出来时在子会话上另加会话级上限，否则一个长任务可以吃掉当天全部额度。

## 3 压缩
- 摘要中出处锚点（文件、页码、章节、表号、来源 ID）是否原样保留，目前只靠摘要模板的指令约束，没有机械校验。
- 没有做后台增量会话记忆（Claude Code 的 SessionMemory：后台分叉 agent 按增量维护一份固定模板的笔记，压缩时直接拿它当摘要，不再同步调一次模型）。现有替代是压缩时放回确定性的文件清单和 skill 当前正文、租户记忆。复查条件，有真实数据后判断，阈值到时再定：
  - 一个租户多久触发一次压缩。
  - 单次压缩的耗时、成本、失败率。
  - 压缩之后的下一轮，用户是否重复提供了已说过的信息，或出处锚点是否丢失。
  - 压缩频繁、摘要质量明显差、或压缩的等待被用户感知（可先考虑回复发出后再压缩，现在是调模型前同步压缩），才回头做。
- 压缩的摘要调用没有传 tools，和主调用的前缀不一致，隐式缓存多半命中不了；各家厂商的缓存时效没有实测。`trim` 的触发线、保留条数和清理名单的初值都没有用真实轨迹调过，看轮数、成本、来源覆盖、一次答对率再定。
- 压缩后放回的文件清单只有名称、类型、大小，没有按会话或场景过滤；租户文件很多时只放最近的 `restore_files_max` 条。

- 永续会话里仍读整段日志的地方：`CitationHook` 在 `deliver_file` 前核对出处，要看本会话所有成功的工具调用，证据可能来自压缩切点之前，所以不能按 `read_live` 截断。只在交付文件时读一次，目前不是瓶颈；日志大到明显变慢时，改成在工具结果旁记出处索引，不再回读原始事件。

## 4 hook
- `user_only` 只防住"本轮读到了不可信内容"和"remember 的内容不是用户本轮说的"。`forget` 没有内容可比对，更早的 turn 里读到的注入仍可能诱导它在一个干净的 turn 里忘掉用户的偏好（行都留着，用户再说一遍就能恢复）。内容比对按去掉标点后的字集合算，用户措辞和模型转述差得很远时会误拒，模型按提示改成原话就能通过，误拒率没有实测。
- 出处校验只核对写出来的引用，不要求"基于文件的回答必须有引用"：模型不写引用就不会被拦。要不要在本轮调过 `read_file` 而回答没有引用时拦一次，等看到真实轨迹再定。
- 引用校验只认摘抄是否出现在所引的块里，不核对模型的转述是否忠于摘抄；数字单位、同比环比这类语义错误查不出。OCR 块的摘抄能通过校验，但原文本身可能是识别错的。
- 纯文本（txt、csv）的 `read_file` 内容不带行号，模型要自己数行；核对不通过时会告知摘抄实际所在的行。
- 文件名在租户内唯一由登记时改名加数据库唯一索引保证。同名多份（理论上不会出现）时引用核对直接判不通过。
- `ask` 决策没有渠道能询问，按拒绝处理（E6004）。console 或企微支持确认后接入。

## 5 存储
- 热词表的写入路径未做（公共 `asr_hotwords` 只能读）。
- 公司对齐：`resolve_entity`（本地优先，没命中才问 QCC `get_company_by_query`）和 `confirm_alias`（租户私有称呼）已做，QCC 客户端在 `eva/tools/qcc.py`，公共层写入口是 `Companies.record_qcc`（只补缺，不覆盖已有 `data_json`）。**已用真实 QCC 探测过 `get_company_by_query`**（唯一匹配、多候选、查无三种都对）：唯一匹配只返回名称和信用代码；多候选（至多 5 个）还带成立日期、法定代表人、状态；返回里有一个写给模型看的「摘要」指令文字，工具不转交，只取固定字段。应答是没声明字符集的 event-stream，必须按 UTF-8 字节解码（已有回归测试）。**腾讯控股这类境外注册的上市主体没有统一社会信用代码**，按名字查「腾讯」返回的是境内子公司，对齐到上市主体要另想办法（主数据里的 sec_code，或联网搜索辅助）。其余维度的 MCP 工具（`tools/list`）还没探。密钥走环境变量 `QCC_API_KEY`，启动时缺失会报 CONFIG_INVALID（和联网搜索一致）；端点域名和路径在 `tools.yaml` 的 `resolve_entity`。
- 公司对齐的取舍：用户说的名字不写进公共别名表（自由文本进公共层有被投毒的风险），所以同一个简称每次都会再问一次 QCC，除非用户确认过（`confirm_alias`，租户私有）。QCC 单价见 `docs/企查查接口价格.md`：配置里对齐搜索和每个维度各一个单价（`tools.yaml` 的 `qcc.search_price_cny`、各维度 `price_cny`），账本按它预扣和结算。数字是 MCP 工具的积分价换算（1 元 = 10 积分），见 `docs/企查查接口价格.md`。对齐的分工（用真实 QCC 探过）：简称展开成全称、错别字改正归模型，工具只做规范化（全半角、括号统一成全角、去空白）、查本地、本地没有再问 QCC，并给候选附判断依据：`sec_code`（主数据里有就带）、`name_match`（候选名和查询词的字面关系）、成立日期、法定代表人、状态。原因：QCC 对简称只返回一串子公司（「阿里」返回 5 个境内子公司），对境外注册的主体返回不相关的公司（「阿里巴巴集团控股有限公司」返回中通快递）或无匹配（腾讯控股），对错别字会精确匹配到字面相同的无名小公司（「宁得时代」）；全称才能唯一命中。所以工具描述要求模型先展开成全称再传、拿不准的错别字先用 `search_hotwords` 按读音找、不认识的公司先 `web_search` 查全称。`web_search` 只用来找名字，网页结果会互相矛盾甚至带篡改文字，不能当事实，信用代码以 QCC 为准。没有候选，或候选全是 `name_match=none` 时，返回里带提示，不让模型拿不相关的候选凑数。集团或品牌对应多家子公司，或候选分不出是哪家时，描述要求模型用 `ask_user` 问一次；这条只靠描述约束，没有 hook，也没测过真实模型的表现（出名的自动判断、不出名的反问），第一次真实对话后看轨迹。**`sec_code` 缺失不等于没上市**：主数据只有 4428 家，全是旧库迁移的上市公司（深交所 2506、上交所 1656、北交所 260），A 股实际更多，贵州茅台就不在里面。热词表（8791 个上市公司名）对应的 4427 家公司已经全在主数据里，补不出新的行，所以不需要补。要补缺口得有别的来源（交易所的上市公司名单，再对每家用 QCC 取信用代码，约一千家、每家 0.10 元），目前没做。
- 境外主体：很多大公司的母公司注册在境外（腾讯控股、阿里巴巴集团控股），没有统一社会信用代码，主数据以信用代码为键，QCC 的 MCP 也查不到，所以**不建境外主体的实体**。处理办法在系统提示里：如实告诉用户这家主体注册在境外、没有境内信用代码，改查它的境内主要运营主体（有多家就让用户选），名单里的境外股东和被投资企业标「未对齐」。对用户不提数据来源的名称。这样集团名（阿里、腾讯、字节）每次都要经过「候选里选境内主体」这一步；要让它免费并稳定，用「集团名 → 境内主要运营主体」清单做成公共别名（`company_aliases`，kind=GROUP，source=offline）：清单在 `tools/group_aliases.yaml`：每个叫法只指向人们说它时通常指的那一家境内主体（primary），旗下其他主体写在 also 里只作备注、不进别名；`python -m tools.seed_group_aliases` 导入（幂等；primary 先查本地，没有再问 QCC，名字完全一致才采用，对不上的跳过并报出来；清单里没有的旧 GROUP 别名会被清理）。现有 10 个集团、15 个叫法、15 行。**清单是人复核的判断，不是事实**：「通常指哪家」带主观取舍，初稿由模型凭记忆写；字节、美团、滴滴三条标了「待复核」。导入时发现模型记的名字有 3 个用精确匹配在 QCC 查不到（北京字节跳动科技有限公司、北京小桔科技有限公司、上海拼多多网络科技有限公司），原因没核实，可能是改名，也可能是搜索没返回；所以每次导入都要核对。清单只是起步，覆盖不到的靠用户确认的租户别名。命中别名且只有一个候选时，工具描述要求模型直接用并提一句旗下还有其他主体。
- 公共别名怎么更新：现在**完全靠人维护，不会自动更新**。写入方只有旧库迁移（一次性，已完成）和 `seed_group_aliases`（人改 `tools/group_aliases.yaml` 再跑），运行时模型和租户都没有写入口；表里预留的 `source=qcc` 没有任何代码在写。冲突的处理：同一个叫法在不同表或不同种类里指向不同公司时，`resolve_entity` 把它们全部作为候选返回，不静默取一个；用户自己确认的租户别名优先于所有公共数据，命中就只返回它。导入集团清单前有冲突检查（`find_conflicts`）：叫法已经是别的公司的全称、简称或别的来源的公共别名，或清单里两个集团用了同一个叫法，整批都不写、报出具体是谁，由人改清单（离线清单自己写的 GROUP 别名不算冲突，改 primary 重导入可以）。**没做的冲突检查**：叫法和其他租户的私有别名是否撞车（私有别名不进公共层，也不应该互相看），以及叫法和热词表的关系。
- 公共别名的半自动更新（都没做，按价值排序）：1）用数据发现该补什么、人来决定：定期统计被多个不同租户确认过同一称呼的 `tenant_aliases`，和每次都要花钱问 QCC 才对上的名字，出一张「建议加入清单」的报表，人审后加进 YAML；现在 `tenant_aliases` 是 0 行，要等有真实对话才有东西可统计。2）多个互不相关的租户各自确认了同一称呼指向同一家后提升到公共层，属于数据飞轮，门槛和防协同投毒没定，见 `docs/待决问题.md`。3）用 QCC 的返回自动补别名：不建议，错别字会被精确匹配到字面相同的无名小公司，写进公共层所有租户都受影响。
- 对账测试的语义：`company_master` 会随使用增长，`company_aliases` 有离线整理的公共别名，所以迁移对账是「源数据全部落到目标」，不是行数相等。以后要把境外主体当实体用，需要新的键（不能用信用代码）和境外数据源，现在没有。
- 公司表的增长：`company_master` 会随使用增长（`resolve_entity` 查到的候选都写入，之后按全称本地命中不再付费）；模型被要求先展开成全称再查，所以每家公司只有第一次见到时付一次搜索费（0.10 元）。`company_aliases` **不会**随使用增长：用户说的名字不是经数据源确认的内容，写进公共层有被投毒的风险（比如错别字被精确匹配到字面相同的无名小公司，所有租户都会受影响）。让别名增长的合规路径是多个互不相关的租户各自确认了同一个称呼指向同一家公司后再提升到公共层，这属于数据飞轮，见 `docs/待决问题.md`。真正花钱的是维度查询（每次 0.5～2 元），已有 60 天缓存；稳定的维度（实际控制人）可以按维度单独设更长的有效期，没做。`data_json` 存的是候选记录原样，多候选时可能比单条查询的字段少，之后做穿透取数时再按需回填；超过有效期重新取数也等穿透工具做。
- 企业数据查询：`query_company`（`eva/tools/query_company.py`）按信用代码查一个维度，只收信用代码、公司必须已在主数据里（没经 `resolve_entity` 对齐的查不了）。维度在 `tools.yaml` 的 `qcc.dimensions` 登记，现有 13 个：工商登记、股东、对外投资、实际控制人、主要人员、董监高关联企业、失信被执行、被执行人、行政处罚、裁判文书、法院公告、立案信息、招投标，**都是用真实 QCC 探过返回形状的**；其余维度（经营异常、股权冻结、工商变更等）要先探一次真实返回再登记。每条记录按会话编号 `q1…` 存 `qcc_results`（含信用代码、维度、取数时间），回答里引用 `【q5「摘抄」】`，`CitationHook` 逐条核对。
- QCC 返回的限制：股东、被投资企业、关联企业**只有名字没有信用代码**，往下穿透要对名字再 `resolve_entity`；自然人、境外主体（如香港中央结算）、简称对不上，按约定标「未对齐」。名单超过 100 条只给前 100 条，返回里会写明「只展示了前 N 条，共 M 条」。数据是当前状态，不带日期，取数时间由我们记。QCC 返回里服务方写的「摘要」「提示」是写给模型的文字，只用来判断是否截断，不转交。
- 工商登记（`single: true`）整个返回就是一条记录。风险类维度没有记录时服务方不返回空列表，而是在说明文字里写「未发现」（`qcc.no_record_text`）：返回里既没有列表也找不到这句话按协议异常（E6009）。这句话是服务方的措辞，改了会变成报错而不是误判成无风险。
- 风险类维度的「没有记录」也进缓存，有效期同 `cache_ttl_seconds`（60 天）：60 天内新出现的失信、处罚查不到，返回里只靠取数时间提示。风险数据是否该用更短的有效期，看实际用法再定。
- 企业数据的有效期现在是一个全局值（`qcc.cache_ttl_seconds`），不同数据变化快慢不同（登记信息、股东慢，失信、被执行、处罚快），要按维度分别设有效期。设计时一并考虑：`resolve_entity` 向企查查搜索时已经拿到成立日期、法定代表人、状态，这些现在只在当次返回里给模型、不带 q 编号、不能引用；是否把它们存下来供后续命中、与 `registration` 的缓存怎么衔接，也属于这个设计，没做。
- `judicial_documents`、`case_filing`、`bidding` 返回的是「近一个时间窗口」的前 30 条，摘要里写的窗口起点（如 2023-07-01 至今）没有进返回给模型的文字，模型只看到「只展示了前 30 条，共 N 条」。
- 还没登记但可用的 QCC 工具：`risk` 服务端的 `get_company_risk_scan`（一次扫描 35 项风险因子的命中数，REST 价 6.00）、`get_company_related_risk_scan`（关联方风险）、经营异常、股权冻结、股权出质等；`operation` 服务端 36 个、`ipr` 服务端 18 个工具未看。`executive` 服务端有 44 个董监高维度工具，只接了 `get_executive_related_companies`。
- QCC 账号的 history 服务端（历史股东、历史高管、历史处罚）**未授权**（`当前用户未授权使用历史信息服务`），按 E6010 不可重试处理；要用先开通。
- 返回缺记录列表、又没有「无匹配项」时按协议异常抛 E6009，不当成空：不知道有些维度对「确实没有记录」是返回空列表还是缺键，遇到再核对。交集（共同股东、共同投资对象）本期不做工具，由模型在沙箱里对名字求交集；按字符串比对，括号全半角、同名自然人会漏或错，用得多了再做确定性的 `find_common`。
- 企业数据查询缓存：`query_company` 的结果存公共表 `qcc_cache`（键：信用代码、维度、人名，所有租户共享），有效期 `qcc.cache_ttl_seconds`（默认 60 天，没有数据依据，看实际更新频率调）。命中不出网、不记账，返回里写明当初的取数时间。**刻意没缓存的**：「没匹配上」（人名是用户随口说的，不往公共层放没经数据源确认的文字，所以同一个错人名每次都会重新付费）和对齐用的名字搜索（键是用户原话，且一次只要 0.10 元，查到的公司已落进主数据）。两个租户同时第一次查同一维度会各付一次，没做合并。没有给模型「强制刷新」的参数，要最新数据只能等过期；用户明确要求时再加。缓存条目没有清理，过期的行被下次查询覆盖。
- 场景报告的维度覆盖门禁：`Report.scenario(场景, 信用代码, gaps)` 声明场景后，`CitationHook.pre_tool` 在 `deliver_file` 前按 `hooks.yaml` 的 `scenarios.<场景>.required_dimensions` 核对（`eva/hooks/coverage.py`），依据是 `qcc_queries` 留痕。场景名与 skill 名相同：本会话成功读过该场景的 skill（`load_skill`）而报告没声明，就不交付。**残留的洞：模型根本没读 skill、自己零散查了企业数据就写报告，推断不到场景，不过门禁。** `gaps` 的原因只作为"有意没查"的标记，不核对真伪。门禁只看必备维度有没有查、查到的有没有引用，不核对报告正文的"没有记录"这类陈述。
- 实体对齐只用 `get_company_by_query`；`verify_company_accuracy`（核对名称与信用代码是否一致）没接入。
- `Identities.resolve`、`files.register` 的条件插入（`WHERE NOT EXISTS` 加 `UPDLOCK, HOLDLOCK`）在并发下的行为没有测试，现有测试是单连接加回滚。需要两个真实连接提交后清理。

## 6 会话
- 单写入者占用表是进程内的；多 worker 前换成租约，接口不变。
- `Hub` 按租户缓存 `Conversation`（含模型客户端），没有淘汰，租户多了会涨内存。

## 7 企微渠道
- 没有和真企微联调：回调、`sync_msg`、`media/get`、`send_msg` 只用假服务端和真验签/加密测过。上线前要用测试客服号走一遍，重点确认 `errcode` 的含义（限流、token 失效、重复 `msgid` 的返回码）和 `Content-Disposition` 的实际形态。
- 只支持文本、文件、图片和语音（语音转成文字后当文字消息处理，不回显转写结果）。图片按文件登记，回一句"已收到图片"，用户接着提问时模型用 read_file 的 OCR 和 view_image 读；图片本身不触发模型，和文件一致。视频、位置、菜单点击、`enter_session` 欢迎语、`msg_send_fail` 事件都没做；非文本非文件的消息回固定提示。
- 拉取仍是单线程、单进程：一个客服号的 `sync_msg` 和游标只有一个拉取线程在动。多进程要对同一客服号的 `sync_msg` 加锁（游标会被并发推回）；消息队列的认领和处理线程池的"已取出"集合都是进程内的，多进程时同一进程内不会重复，跨进程靠 msgid 去重。
- 对账（`reconcile_seconds` 300）的几个数没有依据：不带 token 的 `sync_msg` 的频率上限文档没给；企微保留未拉取消息多久也没找到，停机超过保留期的消息拿不回来。间隔是保守值，限流返回 `E7002`（可重试），下个间隔再试。没有关闭开关，要停就把间隔配成很大的数。
- 窗口（48 小时）已过的积压消息仍会先跑一轮模型，发送时才发现发不出去（`E7004`），白花模型费用。没有提前拦，因为后面若还有更新的消息，窗口会重置，旧消息作为上下文仍有用。停机超过 48 小时的情形出现后再评估。
- 取消点击的“过期”判断用企微的发送时间（秒）和本机时钟比，两边时钟差超过 `busy_notice_seconds` 时，正常的点击会被当成过期。服务器需要对时。
- 并发阈值（`max_parallel_tenants` 16、`max_queued_messages` 200、模型 `max_in_flight` 8 和排队时限 120 秒）是没有数据的起点，压测后调。沙箱、解析的并发上限（各 2）远低于租户并行数，多用户同时用到时在那一步排队。
- 排队时用户看不到进度：企微 48 小时内最多下发 5 条，不能发"排队中"。排队超时只有错误码，用户收到的是"没有处理成功"的固定提示。
- 可重试失败的租户被暂停到那条闲置 `claim_idle_ms` 后重试，期间该用户后续消息不处理；失败条目一直重试直到成功，没有次数上限和死信（见下一条）。
- 可重试错误无次数上限、没有死信：事件闲置 `claim_idle_ms` 后被反复认领，用户在此期间收不到任何消息。
- 回复发送失败（网络、限流）发生在 turn 已正常结束之后，重投时会被去重跳过，这条回复丢了；客户端只在网络层立即重试一次。回复用确定性的 `msgid` 发送，但没处理"企微拒绝重复 `msgid`"的情形。
- 回复（文本段加文件）超过剩余配额时整条不发（`E7004`），用户收不到内容。长文已改成短提示加 md 文件，常见的长回复只占 2 条；一次交付多个文件加文本超过 5 条仍会整条不发。
- `access_token` 缓存在进程内，多进程各取各的，企微侧同一 secret 的 token 会互相顶掉，多进程前移到 Redis。
- 回调服务用 Flask 自带的开发服务器；上线前换成 WSGI 服务器，并确认 1 秒内回 200 的压测。
- `_report` 只打印到标准错误；接入日志体系后替换。

## 8 沙箱
- docker 后端已在服务器（Docker 24、gVisor）上用真实的 `DockerSandbox` 冒烟过：库可用、会话内文件保留、断网（内网和公网都连不上）、根只读、非 root 且文件归应用账号、内存超限 E8005、超时 E8002 且不留容器、不合规产物 E8004。没覆盖的：并发压力、`pids` 限额、符号链接产物被拒（Windows 上没有权限创建符号链接，该测试被跳过）、runc 以外的 runtime 切换。
- 镜像 `eva-sandbox:latest` 只构建在这一台服务器上，没有镜像仓库；换机器要用 `sandbox_image/runtime/build.sh` 重建。
- 文件交付（`deliver_file`，企微 `media/upload` 加文件消息）和长文转 md 文件只用 mock 和模拟器测过，没有连过真实企微。上传接口的细节（`type=file`、5 字节到 20MB、素材 3 天有效、multipart 字段名 `media`）来自旧项目的实现，本地企微文档里没有上传页，要有测试客服号时核对；文件消息在微信里的展示和 md 文件能否直接打开也要实测。交付的 PDF 靠模型在沙箱里自己生成，没验证过沙箱镜像里有没有 PDF 库和中文字体，没有的话要补进镜像。发送失败发生在 turn 结束之后的丢回复问题（见第 7 节）同样适用于文件。`write_file` 的符号链接防护（每一级路径都不跟随）也因 Windows 无权限建链接而被测试跳过，需在 Linux 上跑一次。
- 沙箱里的代码不能调模型。需要"模型网关"（只放行网关，绑定租户的一次性令牌，调用走统一调用层），做 LLM 重建解析、VL 识别扫描件的批量脚本时再做。
- 默认断网。要放行外网，先在宿主上做出口策略（拦住内网和本机段），容器默认网络能直连同机的数据库和缓存端口。
- `run_python` 镜像不含 soffice、tesseract；文件解析用单独的 `eva-parse` 镜像（见第 1 节）。
- `max_workdir_bytes` 只在运行结束后检查，单次运行期间可以写满磁盘直到超时；挂载的工作目录没有配额。
- 空闲回收随 `run` 触发，进程不处理请求时不回收；回收失败会让触发它的那次运行失败。
- 并发上限是进程内的信号量，多进程各算各的。
- local 后端在 Windows 上，父进程退出后遗留的孙进程不会被杀（POSIX 上按进程组杀）；只用于开发机。
- 同机部署：沙箱和数据库、缓存同机，内存余量有限；压测后评估独立宿主机组。
- 解析沙箱的单文件上限（`parsing.yaml` 的 `sandbox.max_file_bytes`，470MB）按 4 小时录音的 wav 定，对解析沙箱里所有产物生效，不分扩展名。恶意文档可以产出一张接近上限的 png，宿主读取留给视觉模型的图时会整个读进内存。要堵住需让沙箱层的上限按扩展名单独配（只放宽 `.wav`），没做，因为目前只有企业租户上传。`Audio` 启动时核对上限容得下最长录音的 wav（`asr.long.max_seconds`），改时长或采样率时它会拦住不一致的配置。
- 长录音在宿主里整段读成 bytes：4 小时的 wav 约 460MB，切段后再复制一份，峰值约 920MB，解析并发 2 时可能到 1.8GB。服务器上没实测内存余量。要降峰值，改成沙箱产物按路径落盘、切段按文件读写（旧项目就是这样做的），要动 `Documents.prepare_audio` 和 `audio_split` 的接口。
- 4 小时录音在沙箱里的转码加提音量耗时没测，解析沙箱时限是 300 秒，工作目录在提音量时同时存在两份 wav（约 920MB，上限 1GB），余量很薄。
- `sandbox.yaml` 的 `max_input_bytes` 在配置里定义了，代码里没有任何地方用它，沙箱没有输入文件大小限制。录音的输入由 `parsing.yaml` 的 `max_file_bytes`（30MB）把关，其他调用沙箱的路径没有。

## 9 报告（skills/report）
- 报告必须用组件库（`save_pdf`、`save_docx`）生成才带引用清单。本会话成功调用过 `uncited_tools` 里的取证工具（`read_file`、`query_company`、`web_search`）之后，没带清单的 PDF、docx 不交付；没用过取证工具的（闲聊、回传用户自己的文件）不管。局限：md、xlsx 等没有清单机制，管不到；用户自己上传的 PDF 在读过文件后也不能原样回传。
- docx 的清单放在 `customXml/eva-citations.json`（自定义部件，关系类型是自拟的）。python-docx 能读回、LibreOffice 能转 PDF，但**没有在 Word 里实测打开**；书签跳转、页码域、表格列宽在 Word 里的表现也只在 LibreOffice 里看过。
- docx 不支持 svg 图片，会报错让模型改存 png。PDF 和 docx 的版式不完全一致（例如 docx 的列表间距偏松）。
- 没压测的情形：很长的表格跨多页、超长单元格、几十条引用、大图。图片整张以 base64 内嵌进 HTML，大图会占内存。
- 沙箱里出一份 PDF + docx + md 的冒烟用了约 14 秒（gVisor 下加载 Noto Sans CJK 和 matplotlib），在 60 秒的超时内；两个并发渲染时 512MB 内存是否够没压测。镜像从 399MB 涨到 535MB。
- 服务器上的 `eva-sandbox:latest` 已重建带上 WeasyPrint 和 Noto Sans CJK，旧镜像留作 `eva-sandbox:before-report` 标签，确认稳定后可删。`eva-parse` 镜像未动。
- 没有场景 skill 声明“默认出报告”，现在只有“用户明确要求”这一条会触发。本机 Windows 开发时 LocalSandbox 用本机 Python 渲染，字体取 Microsoft YaHei。

## 企微模拟器（tools/wecom_sim）
- 只模拟企微的 sync_msg、素材下载、发消息；不验签、不走回调，也没有视频、客服事件入口。页面成功不等于企微验收通过。
- 语音由页面"录音"按钮用浏览器 MediaRecorder 录制，格式是 webm/opus（Safari 为 mp4），不是企微真实的 amr；worker 固定按 `.amr` 交给转写，只验证了 ffmpeg 能按内容解码，整条转写链路没跑过。浏览器录音长了容易超过 `voice_limit_mb`（2MB），超限时渠道会回"语音没有收到"，要测长语音得调大这个配置或分段录。手机用局域网 HTTP 访问时浏览器会禁用麦克风，需要 HTTPS。
- 图片超限时素材取回来不是图片，是按 worker 里的假设模拟的，企微的真实行为未知（见上面企微图片、语音、视频超限一条）。
- 处理和真实 worker 一样按租户并行。重启后上次没处理完的消息会按崩溃恢复被重新认领处理（同样的消息 ID 已处理完的会被去重跳过）。
- 默认端口 5001（5000 常被旧的 blackbox_ui 占用）。队列和游标用 Redis 前缀 eva_sim，与正式前缀分开。

## 联网搜索（web_search，智谱 Web Search）
- 网页引用只证明摘抄来自搜索返回的内容，不证明网页内容属实。聚合站（搜狐、百家号）占了结果里的多数，来源层级没有分级；网页与用户文件不一致时以文件为准，只靠提示词规定，hook 不检查。来源分级后续做。
- `web_results` 不随会话清理，也没有留存期限；量小（每次最多 10 条、每条正文不超过配置字数），数据多了再加清理。
- 回答里用到了网页内容但没有写网页引用，hook 不拦，和文件引用一样。
- 429、额度或余额耗尽、服务方限流的真实响应没有探到，目前按状态码分：429 和 5xx 是可重试的 E6007，其余 4xx 是不可重试的 E6008。余额耗尽的实际状态码和错误体待遇到时核对。
- 失败的调用（超时、5xx）服务方是否计费未知，按"失败不收费"释放预扣；若实际会收费，账本会低估。
- search_domain_filter 传 www.cninfo.com.cn 时返回 0 条，没有暴露给模型；要按域名限定时单独探。
- 并发闸是进程内的，多个进程各有各的上限。
- 聚合站（搜狐、百家号）占了结果里的多数，出处层级低，回答里必须标网络来源。

## 录音校订（eva/tools/proofread.py、skills/audio-record）
- `eva/loop/turn.py`：纯文本输出撞到 `max_output_tokens`（8192）会得到 `TurnEnd.OUTPUT_LIMIT`，被截断的半截文字仍然发给用户。主 agent 现在不写长文字，风险小，暂缓。
- 公司名核实仍由主 agent 用 `web_search` 做；子 agent 机制（`架构设计.md` §7.4）建好后迁过去，让它自己搜索、判断、再搜索。
- `finish` 报错时主 agent 曾反复调试到 `max_steps`，SKILL 只写了"按报错改参数再重跑"，没有重试次数上限。

- 企微长运行取消入口和一轮里的 5 条配额：模拟器里"已收到文件"两条加通知一条已占 3 条，取消入口因额度不够发不出（E7004），开发配置下再发修改清单，最终 PDF 被存进待发队列，要用户回复才补发。线上默认不发修改清单，开发配置下做端到端时会遇到，读 PDF 可以直接去沙箱目录。
- 同一会话写消息时偶发 `SEQ_CONFLICT`（E3001，期望序号比实际下一个序号小 1），一轮端到端停在第 67 步，重启模拟器后同一会话续跑完成。没有查原因，疑似取消入口或"已收到文件"的写入与主循环抢序号。
- 涉及公司表缺法人：公司主数据里 `data_json` 为空的公司（旧库迁移来的，如湖北聚石新材料、广东聚石化学）本地命中时没有法定代表人，`resolve_entity` 现在只带出已存的。数据飞轮要做的是：本地命中却没有法人时查一次企查查，用 `record_qcc` 回填，之后不再花钱。还没做。
- 问答分界处的识别错误：识音（`qwen-audio-3.1-asr-flash-filetrans`）把受访人的应答"对"贴在提问人问句的末尾（`...提供担保那个对？`），校订模型又把它当口头禅删掉，担保这一问在最终稿里没有回答。"对"在文字上分不出是提问人的附加问还是受访人的应答，写规则会拆坏正常的"对吧""是吧"，同一处还有"母公司"被听成"咱们公司"、一句听不清的话被听成"农行的"。要在识音一侧解决：查它能否给词级时间戳或说话人切换点，有了才能在校订时判断。
