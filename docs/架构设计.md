# EVA 架构设计（已决定部分）

> 只记录已和用户对齐的结论。未决问题见 `待决问题.md`，不在此重复。
> 借鉴来源见 `参考-harness源码.md`。

## 0 设计立场

目标是一个**真正自主的 agent 系统**，不是"给传统表单系统接一个 LLM"。

- 现有代码是旧流水线的实现，**不是新设计的前提**。目录、模块名、接口、契约、枚举、状态机、配置格式都不继承。
- 判断标准：新增一项能力，是不是只需要"加一个工具或一份 skill"，而不用改控制流。如果要改流程代码，说明又在建表单系统。

### 表单系统反模式（出现任何一项就停下来重审）
- 先用意图分类器把用户输入归到枚举场景，再走该场景的固定流程。
- 用槽位、等待态、攒批状态机管理一次对话，让模型只填表。
- 流程段之间用定义好的信封或 schema 传递，段的顺序由代码写死。
- 用枚举限制模型"能想什么"（意图枚举、动作枚举）。工具调用的参数可以有 schema，模型的决策不要有。
- 每个场景一份 manifest，列出维度、工具、预算。加能力要改多处配置。
- 验收只看 schema 通过，不看能力。

## 1 目标形态

一句话：**决策权归模型，确定性归工具，约束归护栏，正确性归产物门禁。**

- 只有一套 agent 循环，按配置区分运行方式：工具集、预算、模型、是否允许 fan-out。
- 需求有两种：**对话回合**要秒级返回且便宜，只用只读或便宜的工具，可以 `ask_user` 停放等待；**长任务**（关系穿透、尽调报告）要大预算、长循环、可 fan-out。
- 原则：对话回合不能被长任务阻塞，长任务由对话侧通过 `start_task` 启动。
- 长任务是**子会话**：`start_task` 创建子会话，有自己的日志、与父会话的关联、收窄后的权限和预算。同一套代码、不同配置，不需要单独的进程。`start_task` 立刻返回，对话 agent 回一句"收到"。子会话结束后，结束摘要作为一条消息投递给父会话，由对话 agent 决定怎么告诉用户。
- 运行方式：每个事件（用户消息、控制事件、子会话结束）入队，worker 获取该会话的写入权（租约），按会话 ID 从日志重建 agent，运行到空闲后释放。worker 中途失败，租约过期后由其他 worker 凭日志和崩溃修复接着做。
- MVP 单进程运行，租约用进程内锁。日志追加的期望序号唯一约束照常实现。需要多 worker 时换成 Redis 租约，设计不变。
- 对话和任务进度的事实来源是持久化的 transcript（append-only，含停放的 tool_call，可 resume），不另建对话状态机。
- 资源类记录（文件、费用、投递）按各自的约束设计，是否需要状态机待设计时判断。例如投递窗口可由"用户最后消息时间"和"窗口内已发条数"推导，计费需要不可变事件加幂等加预算预扣的结算或释放。

## 2 承载方式的判断方法

新增功能按下表判断，不凭习惯。

| 条件 | 承载方式 |
|---|---|
| 每次必做，或做错会出事故（泄露、重复扣费、封号） | 基础设施或 hook，模型不参与 |
| 需要判断做不做、做哪个 | 工具（代码执行，模型选择调用） |
| 需要判断怎么做，且无法预先枚举 | skill 加沙箱 |

- skill（`SKILL.md`）只写判断和成本阶梯，确定性抽取下沉成脚本。
- 设计纪律：**skill 数量 ≪ tool 数量 ≪ 自动化步骤数量**。
- 成本优先级：自动执行 > 脚本 > 免费检索 > LLM 精读 > LLM 全读。

## 3 渠道和存储的边界

**产品形态是 DeepSeek、豆包这类对话助手。企微只是 MVP 阶段的接入渠道，以后会换成网页前端。** 渠道的所有限制只存在于渠道适配器内，agent 核心不感知，迁移时整块删除。

- agent 核心只产出与渠道无关的语义事件：流式文本、最终回复、进度、`ask_user`、附件。核心代码里不出现"48 小时""5 条""20MB"这类渠道数字。
- 渠道适配器负责：接收（回调、验签、解密、归一化、msgid 去重、debounce、文件下载）、发送、外部用户 ID 到内部会话 ID 的映射、渠道特有的大小和长度限制。
- 投递策略是适配器的接口：`decide(会话, 事件) → 发送 / 合并 / 延后`。
  - 企微实现：统计窗口内已发条数，合并多条进度、只发最终回复；窗口关闭时把消息存入待发队列，用户下次发消息后补发。
  - 网页实现：永远发送，支持流式。
- 适配器可以向 agent 暴露能力描述，不暴露具体数字。例如"支持流式""可主动推送""消息风格偏短"，用于决定提示词和是否开放某些工具。企微下 agent 看到"不可主动推送"，就不会尝试中途汇报进度。
- 对话 Agent 每轮的最终回复由适配器自动发出。`ask_user`、`start_task` 是工具。长任务运行期间不向用户提问；进度事件由适配器按渠道能力决定是否展示（企微只发"收到"和最终结果）。
- 长任务完成通知、`ask_user` 的超时和提醒，核心只声明事件，"发不出去怎么办"由适配器处理。

**多用户并发（企微实现）**：拉取和处理分开，互不等待。
- 拉取：回调只入事件队列。拉取线程按事件做 `sync_msg`，把每条客户消息写进 Redis 消息队列，一页都入队后才存游标、确认事件。拉取不碰模型，不会被某个用户的长任务拖住。
- 对账：回调只是提示，丢了（服务停过、重试用完、Redis 抖动）就没人触发拉取。所以启动时和之后每隔 `reconcile_seconds`，对每个存过游标的客服号不带 token 按游标补拉一遍，走同一个拉取、同一个游标、同一个入队，已拉过的不会重复。某个客服号失败只上报，下个间隔再试。停机期间用户连发的消息，恢复后逐条按序处理，不折叠。
- 取消点击在拉取线程里立即生效，只作用于该租户当前这一轮。点击的发送时间早于这一轮的开始，就是过期的按钮（比如停机前点的），按“没有进行中的任务”回复，不误停后面的运行。
- 处理：从消息队列取出，按租户分道。同一租户一条一条按顺序处理（同一会话只有一个写入者），不同租户并行，同时处理的租户数有上限（`max_parallel_tenants`）。处理完才确认并删除队列条目。
- 内存里已取出未处理完的消息有上限（`max_queued_messages`），满了就先不取，积压留在 Redis。
- 可重试失败的消息不确认，该租户后面的消息也先不处理，等这条闲置后被重新认领，仍按原顺序。不可重试失败只影响这一条。重复入队或重复认领靠 msgid 在核心侧去重。
- 不按任务轻重分流（那是意图分类器）。限流放在昂贵资源上，各自一个进程级信号量、上限走配置：模型请求（`model.yaml` 的 `concurrency`）、沙箱（`sandbox.yaml`）、文件解析（`parsing.yaml`）、联网搜索（`tools.yaml`）。普通对话只占模型名额；用到重资源的任务在那一步排队，排队超时返回可重试错误，不影响别人的聊天。
- 阈值是起点，压测后只改配置。

**文件交付与长文转文件（企微实现）**：核心只登记"这个文件要交给用户"，怎么送是适配器的事。
- 交付：模型调 `deliver_file(file_id)`（文件须先经 `write_file` 保存，或本来就是租户的文件）。工具把文件读出放进本租户的发件箱，turn 结束后随 `Reply.files` 交给渠道，下一个 turn 开始前清空，发过的不会再发。核心不判断文件能不能发、多大。
- 发送：适配器先上传全部素材（上传不占配额），再把文本段数和文件数加在一起预留配额，不够就一条都不发（E7004）；然后先发文本，再发文件。上传失败时什么都没发出。超过企微文件大小上限的文件不发，回复末尾告诉用户，同时上报。
- 长文：文本切出的段数超过 `max_text_parts`，改成一条短提示加一个 md 文件，全文在文件里。这是适配器自己的行为，核心的回复文字不变；网页渠道没有字数限制，不需要它。
- 最终报告是 PDF：模型在沙箱里生成、保存、用 `deliver_file` 交付；中间过程的长回复由适配器转成 md。
- 交付记录：`deliver_file` 登记交付时同时写 `file_deliveries`（哪份文件、哪个会话、报告声明的场景和公司）。用户以后说"之前的那份报告"，模型用 `list_files` 查这张表找回 file_id，再 `deliver_file` 重发，不依赖会话里还留着 file_id。原件和交付物不设保留期，不自动删除。
- 选项菜单：agent 带选项提问时，适配器把问题放进菜单的起始文本，选项各占一个菜单项（项目文字是"序号. 选项"，超长从尾部截断但保留序号），整条占一条配额。选项超过菜单上限、问题超过起始文本上限、同时还有文件、或额度不够发菜单，就改发编号文字，选项一个不丢；额度不够时走已有的"回复 1 继续"。点击不刷新窗口和配额，所以选完一个再问下一个也不指望额度重置。三个企微上限在 `configs/wecom.yaml`。

**报告（skill + 沙箱）**：`skills/report/` 是一个 skill，不是工具，也不是每个场景一套模板。
- 判断写在 `SKILL.md`：什么时候出报告（场景 skill 声明默认出，或用户明确要求），什么时候不出（没有实质内容、材料读不到、只是问答）。最终报告默认 PDF，用户要求其他格式听用户的；中间过程的长文字由渠道转 md 文件，不归它管。
- 内容与版式分开：`scripts/eva_report/` 是组件库，模型拼的是一棵与格式无关的文档树（封面、标题、段落、列表、表格、图、提示框、页分隔），树就是 JSON，可存盘再读回。输出层有 PDF（HTML + WeasyPrint）、docx（python-docx）、md 三个渲染器，都读同一份 `scripts/theme.yaml`（字体、七个颜色、四种提示语气、字号、页边距）。换字体配色只改这个文件。
- 引用：文字里写 `【文件名#b12「摘抄」】` 或 `【w3「摘抄」】`，树按全文出现顺序生成一份引用清单（相同引用共用一个号，网页引用必须登记来源），渲染成正文角标、文末来源，角标和来源互相跳转，网页来源带链接。
- 核对：清单随文件带走（PDF 的附件 `eva-citations.json`，docx 的自定义部件 `customXml/eva-citations.json`）。`deliver_file` 前，`CitationHook.pre_tool` 取出清单，逐条做和回答相同的核对，网页引用的链接还要和本会话 `web_search` 存的一致；不通过拒绝交付并给出原因，让模型改了重新生成。没有清单的文件（用户自己的文件、没用组件库生成的）不核对。
- 渲染前做字体自检（排一段探针文字再抽回来比对），缺中文字体就报错，不出满篇方块的文件；渲染时只认内嵌图片，任何外部地址都拒绝。
- 沙箱镜像带 WeasyPrint、Pango 和 Noto Sans CJK；字体缓存在构建时生成。

**可拆卸的验证方法**：从第一天起同时实现一个最简适配器（控制台或网页）。删掉企微适配器及其配置后，核心代码和测试必须仍能跑通。

**数据库：agent 不连库，只调领域工具。**
- 工具按业务语义命名（如 `search_company`、`get_user_history`），租户过滤由 hook 和存储层强制加上。
- 不提供通用 SQL 工具。
- transcript 持久化、台账、记账、文件登记、幂等落库由循环自动完成，不做成工具。

**资源类记录：都不建状态机，状态从事实推导。**
- 投递窗口：不建表。企微适配器在 Redis 里按（客服号，用户）记"用户最后消息的发送时间"和"此后已发条数"，用户每发一条就重置，键随窗口过期。不从 transcript 推导：确认回复、固定提示、切成多段的回复都占配额，但不是 transcript 里的事件。
- 计费：只追加的账本事件，类型为预扣、结算、释放，同一次预扣的三类事件共用预扣 ID。余额和已用额由事件累加得出，账户上不存状态字段。幂等键是模型调用 ID，重复写入直接拒绝。worker 崩溃留下的"有预扣无结算"，由定时清扫按"该次运行的租约已过期"补写释放事件，预扣本身不带超时字段。
- 文件：一张登记表，字段有租户、内容哈希、对象存储键、大小、类型和一个简单状态（已上传 / 可用 / 已删除）。状态之间没有转换规则，直接覆盖写。
- 长任务：不另存状态列。运行中、停放、完成、失败、取消从 transcript 和运行记录的起止事件推导。

**存储层表结构**：SQL Server 同实例新建库 `eva_perf`，旧 `ccm` 原地只读作迁移源。九张表：tenants、sessions、transcript_events、ledger_events、file_registry、company_master、company_aliases、tenant_aliases、asr_hotwords，列、约束与 MinIO 布局见 `docs/新表设计.md`。飞轮种子的表（事实、来源、文档原件）暂不建，飞轮设计时定。

## 4 沙箱

沙箱是通用的"执行不可信代码或字节"能力，不绑定文件解析。

- 适用：模型自写代码、不可信文件解析、数据处理脚本。
- agent 循环和 hook 留在宿主，不放进沙箱。原因：hook 要用凭证和计费状态，放进沙箱隔离就失效；大多数工具是检索和查库；每会话起容器会拖慢对话。
- 默认断网，凭证和存储客户端不进沙箱，数据只通过文件进出。
- 产物进入模型上下文前，在宿主侧校验。
- 镜像独立构建，不与主服务共享依赖树。

- 对话 agent 开放 `run_python`。风险是资源消耗和输出质量，不是越权，由预算上限和产物校验约束。
- 生命周期：每次调用一个一次性容器，跑完销毁，不保留进程和变量。会话工作目录在宿主上（`{work_root}/{tenant_id}/{session_id}`），挂进容器，会话内的文件保留，空闲超过配置时间回收。子会话（长任务）使用独立的工作目录，不共享父会话的。需要长期保留的产物必须经写文件工具落到对象存储，不能只留在工作目录里。
- 不按"一个文件一个沙箱"：那是不可信文件解析的隔离粒度。`run_python` 的隔离边界是单次调用，解析文件时把那一个文件只读挂进去即可。
- 模型调用不进沙箱。需要 LLM 或 VL 的步骤（重建解析结果、识别扫描件）在宿主侧的工具里经统一调用层完成，沙箱只做渲染页图、OCR、格式转换这类确定性的活。沙箱里的代码想自己调模型，需要"模型网关"（只放行网关，凭证为绑定租户的一次性令牌），尚未做。
- 网络：默认断网。宿主上的数据库和缓存容器与沙箱同机，容器默认网络能直连它们的端口，要放行外网必须先有出口策略拦住内网。
- 产物校验由宿主侧的沙箱工具在返回路径上完成，不靠模型自觉，也不另设一层：检查输出大小、文件类型白名单、是否文本。超过大输出阈值的走 7.8 的溢出。校验不通过返回结构化错误码，不静默截断。
- 隔离技术：沙箱执行器定义成接口（`eva/sandbox/`），agent 核心和工具只依赖接口。后端由 `configs/sandbox.yaml` 的 `backend` 选择：`local` 是宿主子进程（开发机，只有超时、输出上限和环境变量白名单，不隔离网络和文件系统）；`docker` 是一次性容器（服务器：断网、只读根、去掉全部 capability、内存/CPU/进程数限额、以宿主进程的 uid 运行，运行时默认 gVisor `runsc`）。
- 后端如实报告隔离程度（`full` 或 `partial`），`require_enforcement` 要求的程度高于后端能做到的，启动即报错，不降级。对外环境配 `docker` 加 `full`，不在代码里按环境分支。
- 失败分两类：容器起不来（docker 不通、镜像缺失，退出码 125/126/127 且 stderr 是 docker 客户端的报错）是沙箱故障 E8001；代码自己的失败（退出码非 0）是正常结果，原样交给模型。超时 E8002，输出或工作目录超限 E8003，产物不合规 E8004，内存超限（退出码 137）E8005。
- 同机部署：服务器上沙箱和 SQL Server、Redis、MinIO 等同机，并发上限（`max_concurrency`）和单容器内存都走配置；独立宿主机组留到压测后。

## 5 文件读取

读时解析，不设入库流水线，不设固定的读取阶梯。

- 一个 `read_file` 工具，按文件类型读取，分页返回，带锚点。首次读取时解析，结果按（租户，文件内容哈希）缓存，之后的读取直接命中，同一租户内跨会话和长任务共用。不跨租户共享，否则命中缓存会暴露别的租户传过同一份文件。
- 分页的单次字节上限放配置，必须小于 7.8 的溢出阈值（读取工具本身不参与溢出）。超出时返回截至哪个锚点和下一段从哪里继续，由模型自己翻页。
- 当前只实现纯文本类（扩展名在 `configs/tools.yaml`），按行号范围给锚点，其余类型返回 E2002；上传由渠道适配器负责，登记和写原件由装配层完成。
- 图片和扫描页：`read_file` 先给 OCR 文本（原文，可引用）。文档里的内嵌图（不论 OCR 读没读出字，读出的文字单独成块在前）和 OCR 没读出文字的上传图片、无文字层的扫描页（空白图不看，每份文件有张数上限）在解析时由宿主交给 `vision` 模型描述：沙箱没有网络、不持凭证，只在文档里留占位块并把图传出，宿主经统一调用层问模型，描述写进 `VISION` 块。块上标明"看图识别，非原文"，引用校验拒绝这类块。占位块和图的 sha256 随解析结果缓存，图本身按哈希存对象存储，描述按图的内容哈希缓存；读取时补描述，没看成的块改成未读并在警告里给出块号和错误码，下次读取只重问这些图，不重跑沙箱。描述不够用时，模型调 `view_image(file_id, question)` 带具体问题再看上传的图片，或加 `block`（看图识别块的块号）追问文档里的内嵌图，结果同样不可引用。主模型始终只收文字，看图模型没有工具，图里的文字注入不会触达有工具的模型。
- 统计、格式转换、编辑 docx 和 xlsx 走沙箱里的 `run_python` 加 skill，不单独做工具。
- skill 的承载：`skills/<名字>/SKILL.md`（frontmatter 的 `name` 必须等于目录名，`description` 必填）加可选的 `references/`（只收 .md，按需读的细节）和 `scripts/`。启动时全部读入校验，任何一个不合格服务就启动失败，不跳过；运行中改了 `skills/` 下的文件不用重启，按 `check_interval_seconds` 比对文件指纹，变了就重新加载，新内容不合格则保留上一份合格的并报一次 `CONFIG_INVALID`（显式降级）。每个对话在每个 turn 开头取一次快照，一个 turn 内清单、正文和脚本来自同一份。正文、参考文件、description 和脚本总量的上限在 `configs/skills.yaml`。系统提示末尾列出名字和一行描述，模型用 `load_skill(name)` 读正文，再用 `load_skill(name, file)` 读正文里指引的参考文件（都不走溢出）；脚本由 `run_python` 在每次运行时放进工作目录的 `skills/<名字>/`，模型 `sys.path.insert` 后 import，它们既不算上传的输入，也不会被当成新产物。
- 租户层：除了仓库里的公共 skill，每个租户在 `tenant_skill_versions` 表里可以有自己的补充（叠在同名公共 skill 正文后面，冲突时以补充为准）和租户独有的 skill（公共层没有的名字）。只存正文，没有脚本，不会出现在别的租户的视图里。表只追加，回退和归档都是新增一行；写入口是 `eva/storage/tenant_skills.py` 里 `TenantSkills` 的 `put / archive / revert`，校验在存储层，坏内容进不了库。对话每个 turn 开头读 `tenants.skills_rev`，变了才重取并叠加。公共层后来与租户层对不上（补充对应的公共 skill 没了、独有的名字被公共层占了）时忽略那一条并报一次 `CONFIG_INVALID`。
- 不预建向量索引，评测显示整文件读取过贵时再加。
- 不可信文件的解析在沙箱执行（见第 4 节）。

**出处锚点**不用坐标，用语义位置：文件、页码、所在章节标题、元素类型（正文、表格、图）、表号或图号。音频转写用时间段。VL 的输出是生成的，章节和页码可能出错，所以引用必须在 hook 或完成关卡里校验，不靠模型自觉：
- 页码必须存在于该文件。
- 引用的原文片段必须能在该页文本里找到（可抽取文本的文件直接比对，扫描件比对 OCR 文本）。
- 校验不通过的引用不得进入报告，返回结构化错误，让模型重读。
- 引用格式：回答里写成 `【文件名#b12「摘抄原文」】`（块号区间 `b12-14`），纯文本文件用行号 `【文件名#L12-15「摘抄原文」】`；格式定义在 `eva/contracts/citation.py`。完成门禁（`eva/hooks/citations.py`，stop hook）逐条核对：文件属于本租户，块号或行号存在，摘抄（去掉空白、全半角统一后）出现在所引的块或行里，摘抄不少于 `configs/hooks.yaml` 规定的字数。不通过的原因（含摘抄实际所在的块或行）注入给模型，次数上限是 `gate_max_retries`。回答里没有引用不拦。
- 网页引用：`【w3「摘抄原文」】`，编号是本会话里 `web_search` 返回的 `[w3]`。搜索结果按会话存进 `web_results` 表，编号在会话内唯一；stop hook 在本租户本会话里按编号取回，核对摘抄出现在该条的标题或正文里（只认模型看到过的那段，不认被截掉的部分），不通过时同样告诉模型摘抄实际在哪一条。网页引用只证明摘抄来自搜索返回的内容，不证明网页内容属实。

ASR：转写是基础设施，热词和 diff 校正是脚本，"这个专有名词指哪家公司"是 skill 加检索工具。

## 6 横切需求（调用层与护栏）

这些是需求，不是模块名。形态在重构中重新设计。

- 所有模型调用（循环、子 agent、工具内部）统一记账、预算、熔断、超时、租户归属，且必须支持 tool use。
- 租户隔离是前提：失败要表现为"查不到"，不能是"查到别人的"。
- 租户粒度：企微下一个租户就是（客服号，外部联系人）这一对。企微是外部客服，用户扫码即聊，接口只能拿到一个用户 ID，拿不到组织和身份信息，所以不存在"客户组织"这一层——和 DeepSeek、豆包一样，一人一份私有数据。同一用户在不同客服号下是两个租户，数据和会话互相隔离，将来客服号增多也不会串。
- 租户与身份分开：`tenant_id` 是系统生成的内部编号 `<realm>_<小写 ULID>`，不含任何渠道信息。渠道里的"这个人是谁"记在 `tenant_identities`：（realm，渠道，范围，渠道用户 ID）四列联合唯一，指向租户。企微的范围是客服号，终端、评测、网页的范围为空。
  - realm 是租户的用途，也是租户前缀，集中定义在 `eva/contracts/`：`usr` 真实用户（企微、将来的网页）、`sim` 企微模拟器、`eval` 评测、`dev` 本地终端。由启动入口决定，不从 ID 字符串猜；存储层的 `Identities` 构造时固定 realm，读写不了别的 realm 的身份，所以模拟器和评测指不到真实用户。
  - 非真实用户的渠道用户 ID 带固定前缀 `<realm>_`（如 `sim_alice`、`eval_案例名`、`dev_local`），只用于辨认和挡住手写的越界输入，隔离靠 realm。企微真实用户的 ID 是企微给的原值，不加前缀。
  - 同一评测名始终解析到同一个租户，所以评测的解析和转写缓存可以复用。
  - 合并账号只往 `tenant_identities` 加一行，不改业务表。第一版的绑定：网页用户登录后得到一个短时效的一次性令牌，随客服链接的场景值带进企微会话，`enter_session` 事件带回令牌，由存储层唯一的写入口校验并绑定。两个租户都已有数据时拒绝（`IDENTITY_CONFLICT`），真合并的操作以后另做。默认各自隔离：拆开比合并难。
- 出站调用可能带出私有信息。QCC 的企业名出站是对齐所必需的，接受。联网搜索的查询词限制长度（配置），完整查询词落日志供审计。
- 预算预扣、出处校验、白名单放在 hook，声明式、可测、跨场景复用。
- 失败可区分：错误码集中定义，标明可重试性。
- 稳定前缀护 KV cache，上下文有压缩策略。

**成本与延迟红线**（护栏，防跑飞，不替模型做决定。数值走配置，初始值评测期再调）：
- 对话回合：工具调用轮数护栏 15 轮，等值成本预算 ¥1/回合。任一触达，循环注入"预算用尽，请用已取得的信息收尾"，让模型自己总结，不硬切断。
- 长任务：总预算初始 ¥20/次，走预扣/结算/释放记账。耗尽即停放，transcript 记结构化错误并通知用户。不设总时长上限，单次调用超时和流空闲超时（7.10）兜住挂死。
- 异步与"收到"：执行形态不自动转换，要不要长任务由模型调 `start_task` 决定，调用即回"收到"。护栏是延迟阈值：回合开始 15 秒无最终回复，适配器补发"收到，正在处理"，之后只等最终结果。运行本来就在后台 worker，用户从不阻塞服务。

**实体对齐：**
- 一个领域工具 `resolve_entity(名称, 上下文线索)`。工具只做确定性的部分：名称规范化、别名表、本地库检索、QCC 查询，返回带统一社会信用代码的候选，每个候选带匹配依据。没有候选时返回空列表且无错误码，数据源故障才抛错误码。
- 候选之间选哪个由模型决定，默认不问用户。模型在回复里写明所选主体和信用代码，用户可直接纠正。只有候选分不出来且选错代价大时，才用 `ask_user` 问，且一次只问一个实体。全称和信用代码一律取自工具返回，不用模型记忆。
- 关系穿透类工具只接受实体 ID，不接受名称，没对齐就无法往下查。最终没对齐的实体在报告里单独标"未对齐"，不进入穿透结果。
- 按需触发：只有要进入穿透查询或写进报告的企业才对齐，访谈中顺口提到的不做。对齐到法人主体，集团下的子公司关系由 QCC 的关系查询工具给出。ASR 纠错不走实体对齐。
- QCC 返回的企业信息存入公共层的公司主数据，以信用代码为键，带取数时间，超过配置的有效期后重新查询。
- 联网搜索是另一个工具，用于冷门、新成立或 QCC 没有的实体，以及辅助判断"是不是用户说的那家"。搜索结果只给模型参考，不作为公司主数据入库。
- 人名暂不对齐。用户确认过的对齐结果存为租户私有别名，下次直接命中，不进公共层。
- 用户明确要求记住的偏好和纠正存在 `tenant_memories`（租户私有，只追加），模型用 `remember`、`forget` 写，生效条目每个 turn 附在系统提示词里。写入只能由用户本轮说的话触发，由 `user_only` hook 机械地挡：本轮调用过名单外的工具就拒绝，内容要和用户本轮的话对得上。
- 用户要换话题、从头聊：模型调 `new_topic`（工具声明 `resets`，成功后由循环写 `context_reset` 并以固定回复结束 turn），企微上整条消息等于 `reset_command`（`新话题`）时由渠道直接让 Hub 写同一个事件，不进模型。此后视图从重置处重新开始，日志原文、记住的偏好、会话本身都不动。这是不再参考，不是删除，回复里不得说成已删除。`new_topic` 同样受 `user_only` 约束。

**公共层写入口：**
- 模型没有任何写公共层的工具。公共层只由基础设施在特定工具返回后写入，目前只有 QCC 查询一条。
- 写入口只接受固定字段的结构化数据，不接受自由文本，不带租户字段。以后加别的来源，另开写入口单独评审。
- 联网搜索结果不回灌公共层，只留在 transcript 可审计。网页文本来源不一、准确性无法校验，还可能被人故意写成给模型看的指令。
- 数据飞轮（公开数据的积累、存储、检索、更新）单独设计，不阻塞核心循环。

**评测：**
- 题目由用户出，rubric 由用户定。来源三路：真实访谈和尽调需求脱敏后的场景题；线上答错收进回归集的失败题（题库增长的主要方式）；专门放"旧流水线答不出、新系统应答得出"的能力题。
- 题目形式是"问题 + 评分点/参考答案"，不是输入输出 JSON 对比。每道题带负向样本：查不到要答"查不到"，不许编造。
- 凡是能确定性校验的（引用页码、引用文本、数字），用代码校验，不用 LLM judge。judge 只判开放性回答质量，模型走配置，定期抽样人工复核。
- 评测跑批把题目喂给同一套 agent 循环，从 transcript 算轨迹指标（轮数、成本、来源覆盖、幻觉率、一次答对率），不写"评测模式"旁路。指标先记趋势，阈值按数据后定。工具级正确性归 pytest，评测集管场景级和轨迹级。跑批和对比的工具见 7.12。

## 7 会话、工具、hook 与子 agent 的约束

> 依据：`参考-harness源码.md`。借鉴的是形状，不是代码。

### 7.1 日志与模型视图分离
- transcript 是 append-only 的完整日志，用于审计、计费和回放。模型看到的是由日志推导出的**视图**。
- 上下文压缩只改视图，不改日志。压缩开始写 `compaction/start`（兼作该会话的压缩锁），结束写 `compaction/end`，失败的尝试也留在日志里。
- 压缩失败要关闭：摘要被截断、为空，都报错，不落不完整的摘要。
- 压缩的切点两侧不能有"有调用没结果"的工具调用：切点只落在用户或助手消息的开头。
- 视图太大时先便宜后昂贵，每次调模型前依次判断。视图 token 数 = 压缩或 trim 之后最近一次真实用量加此后新增事件的估算，没有真实用量时逐条估算。阈值都是绝对 token 数，在 `configs/loop.yaml`，不按窗口比例（窗口 100 万时历史越长每次调用越贵越慢），装配时校验触发线小于模型窗口。
  - **trim**：达到 `trim_trigger_tokens`，且能清掉的旧结果超过 `trim_min_freed_tokens`，就写一条 `trim` 事件（切点和清理的工具名单），视图把切点之前、名单内工具的结果换成占位说明，最近 `trim_keep_recent` 次调用保留。不调模型，一次清一批，不逐轮滑动，前缀稳定才不会每轮破坏隐式缓存。写了 trim 的这一步不再判断压缩：清完没有真实用量，逐条估算是上界、会偏高，等下一步有了 trim 之后的真实用量再判断。名单是结果大、能重新取的工具（`read_file`、`query_company`、`web_search`、`proofread`），`load_skill`、`ask_user`、`deliver_file` 这类的结果不清。引用要对原块核对，模型引用被清掉的内容时本来就得重新读。
  - **压缩**：仍达到 `compact_trigger_tokens` 就整段压缩成摘要，尾部保留约 `compact_keep_tokens`。摘要的输入是 trim 之后的视图。溢出错误也触发一次。连续 `compact_max_failures` 次压缩失败后，压力触发的压缩不再试（溢出触发的仍试），成功一次或上下文重置清零，状态从日志现算。
  - **压缩时放回视图的信息**：压缩结束事件的 `attachments` 记着本会话加载过的 skill 的**压缩时当前版本**（和 `load_skill` 返回的是同一段文字：正文加参考文件清单和脚本路径提示；含租户补充，带哈希，总量封顶，放不下的只列名，已不存在的单独标明）和本租户最近登记的文件清单。内容写进日志，视图只读日志，回放和审计看到的与当时一致。
- 摘要模板按我们的领域写：用户目标、已确认的实体和对齐结果、已取得的证据及出处、待办、用户偏好和纠正。**出处锚点（文件、页码、章节、表号或图号、来源 ID）必须原样保留**，不得被摘要改写。
- 永续会话的日志只增不减，所以循环每一步只读**仍然有效的部分**（`Transcript.read_live`）：最近一次 `context_reset` 之后，且从最近一次成功压缩的切点起。更早的事件已被摘要代替，不再读取。压缩的摘要输入是上次的摘要加切点之前读到的事件；更早加载的 skill 靠上次压缩结束事件里的放回名单接上，连续压缩不丢。需要更早事件的地方（出处核对、交付门禁）各自按需要读，见 `代码遗留问题.md`。
- 压缩调用走统一的模型调用层，带用途标签，和对话调用分开记账。
- 压缩与同一会话的对话回合互斥，期间到达的用户消息排队。

### 7.2 工具
- 每个工具声明并发属性：可并行或独占。独占工具形成屏障。结果按模型给出的顺序提交，不按完成顺序。
- 工具在模型本步输出完整结束后才开始执行，不边接收边执行。本步尝试若失败被丢弃（7.10），其中的工具调用尚未产生副作用。
- 写类工具（扣费、发消息、写库）必须声明幂等性，并按调用 ID 去重。
- 崩溃恢复时，没有结果的工具调用补一条合成结果：
  - 未记录开始：可重试。
  - 已记录开始但无结果：结果未知，只有只读或幂等的操作才重试；有副作用的先核实外部状态或询问用户。
- 用户消息追加到日志之前，先按消息 ID 去重（渠道可能重复投递）。

### 7.3 hook
- 多个 hook 命中同一点时，权限取最严（`deny > ask > allow`），第一个停止原因保留，只输出赢得优先级那一档的理由，追加上下文按顺序累积。
- 每次 hook 调用在日志里写成对的 `invoked` 和 `result`，记录决策、耗时、错误摘要，用于审计。
- hook 改写工具入参暂不支持。
- `ask`（需要用户确认）在没有渠道能询问时按拒绝处理，返回 E6004。

### 7.4 子 agent
- 权限在创建时固定，**只能收窄，不能在运行中放宽**。子 agent 继承父的租户上下文和预算上限，不得自己突破。
- 有委派深度上限，深度持久化，父 agent 恢复后不能把深度重置为 0。
- 子 agent 有自己的 transcript，并记录与父的关系。
- 子 agent 的结束状态从它自己的日志推导（完成 / 超 token / 取消 / 出错 / 被拒绝），不从"进程正常退出"推断。
- 被拒绝的操作不重试，在结果里说明限制，由父 agent 处理。

### 7.5 `ask_user` 停放与恢复
- 停放不需要特殊机制：这一轮结束时，日志以"等待用户回答"收尾，进程内不留状态。工具声明 `parks=True`（没有 `run`，参数里 `question` 必填）即为停放工具：循环不执行它，同一步的其他工具照常执行，turn 以 `waiting_user` 结束，`question` 作为回复展示。一步里有多个停放调用时只停放第一个，其余返回 E6004。
- 选项：`ask_user` 可带 `options`（至少 2 个，互不重复）。模型只表达"这是几个选项里挑一个"，不关心怎么展示，也不自己加序号；`Reply.options` 把选项交给渠道，渠道自己决定渲染成菜单、按钮还是编号文字。编号写法统一在 `eva/common/choices.py`：选项前是"序号. "，用户的回答可能是序号、"序号. 选项文字"或他自己的话，模型按序号对回自己给的选项。企微渲染见渠道一节的选项菜单。
- 恢复：用户回复到来时，按会话 ID 读日志、去重、追加回复、重建 agent、开始新的 turn。
- 重建所需的全部信息（模型、工具集、预算、租户）必须能从日志或会话元数据还原。进程内的运行实例只是缓存，任何 worker 都应能重建。
- 用户的回复写成那次停放调用的 `tool_result`（带渠道 `msg_id`），由 `Writer.append_input` 在启动新 turn 之前写入：有停放调用在等就写成结果，否则写成用户消息。`msg_id` 去重同时覆盖两种写法。崩溃恢复补合成结果时豁免停放工具，因为它的结果就是用户的回复。
- 对话和任务的当前状态从日志与活动事实推导，不另存一份状态字段。
- 同一会话同一时刻只有一个写入者，已有在途运行时抛 E3003。MVP 单进程用进程内占用表，多 worker 时换成 Redis 租约。
- 无论用哪种方案，日志追加都要带期望序号：追加的第一个事件序号必须等于当前下一个序号（数据库里用 `(会话ID, 序号)` 唯一约束）。这是兜底，即使锁失效也不会写乱日志。
- 失去所有权（租约过期）的写入者必须停止，不得继续写；只能重新获取所有权后重新读取日志再继续。

### 7.6 循环、模型与调用层
- agent 循环**自研**，不采用 LangGraph、各厂商 Agent SDK 等框架。
- 模型配置在 `configs/model.yaml`：主选 `qwen-plus`，备选 `deepseek-flash`，只在传输层或可用性失败时切换。另有 `vision` 角色（`qwen3.8-flash`），给解析时的看图和 `view_image` 用，不参与主备切换，必须声明 `input: image`。每个模型声明 `input` 能力。
- 厂商差异（推理强度、关闭思维链、额度耗尽的错误码形态等）放配置，代码里不出现按厂商分支的 `if`。
- 备选模型只在传输层或可用性失败时启用，语义失败不切换。熔断是进程级的，参数沿用现有配置的思路。
- 重试、溢出压缩、截断、切备选的细则见 7.10。
- 模型一步里既没调工具也没给文字（`finish_reason=stop` 且内容为空）时，循环同一步再调 `empty_max_retries` 次，仍空才以 `empty_response` 结束。空的这次照常写进日志，模型视图里跳过这种空 assistant 消息，否则下一次调用会看到它。重试占步数，费用如实计入。

### 7.7 完成门禁
- 采用 Stop hook 的形态：模型想结束（没有工具调用）时，先运行门禁；不通过则把原因作为新输入注入，循环继续。
- 报告的出处校验、票数、完整性等校验都放在这里，不做成独立的流水线段。
- 门禁必须有重试上限，超过上限以失败交付，不得无限循环。
- 预算和最大步数是硬上限。到最大步数时禁用工具，强制输出文字总结。

### 7.8 大工具输出
- 工具的纯文本结果超过阈值（配置项，字节数）时：完整文本存入租户和会话命名空间下的对象存储；模型看到的只有首尾预览加"省略了多少字节、文件标识、如何读取"的说明。替换后的内容不得超过阈值。
- 取回走与第 5 节同一个文件读取工具（分页读，参数 `overflow_key`），不按路径直接读。**存储本身不做访问控制**：`storage/objects.py` 只放行本租户本会话前缀下的键，其他键一律当作"查不到"（E2001）。
- 读取工具自身的结果不再溢出（工具声明 `spills=False`），避免"读取 → 溢出 → 再读取"的循环。
- 阈值 `spill_threshold_bytes` 和预览长度 `spill_preview_bytes` 在 `configs/loop.yaml`，加载时校验两段预览加说明文字不超过阈值；`read_file.page_bytes` 必须小于阈值，装配时校验。
- 循环不连对象存储，由装配层注入 `spill(会话ID, 文本) → 对象键` 回调；没有注入则不溢出。
- 只处理纯文本结果。含非文本块的结果不处理。
- 存储失败时显式降级：保留原结果，在该 `tool_result` 事件里写 `spill_failed`（错误码），不把成功的工具调用变成错误。成功时事件里有 `spilled`（对象键和原始字节数）。
- 日志里的副本同样设上限，日志不是模型上下文，但不能无限增长。
- 对程序化调用方（代码直接取结果），完整结果不变，只有模型侧的副本被替换。

### 7.9 长任务运行期间的用户输入
- 一个会话同一时刻只有一次在途运行。
- 运行期间，用户的普通消息按租户顺序排队，运行结束后依次作为新的输入交给 agent，不丢、不报错。
- "取消"是控制事件，不是聊天内容。由渠道适配器识别并直接触发，不经过模型，不进消息队列（排进去就要等运行结束）。网页用停止按钮。不用文字关键字识别，避免误判。
- 企微没有常驻菜单，取消入口是随消息下发的菜单消息（`msgmenu`，点击后回调是一条 text 消息，带 `menu_id`）。一轮处理超过配置的秒数（`busy_notice_seconds`）仍未结束，适配器下发一条只有"取消任务"的菜单消息。只取消进行中的长运行，普通秒级回合不提供。
- 取消按真实状态分两步回复：点击后立即回"正在停止"；运行写入 `CANCELLED` 后再回"已停止"。没有在途运行时（过期按钮）回"当前没有进行中的任务"，不算错误。企微没有说明点击算不算用户主动发消息，所以点击不刷新下发窗口和配额（见待决问题）。
- 取消在步骤边界生效：步骤之间、沙箱执行和转写中能停；已发出的模型调用要等它返回，已提交给厂商的转写任务不能撤回。已取得的结果保留在日志里，没执行的工具调用补"已中止"结果。取消后用户可以让对话 agent 基于已有结果继续。
- 取消入口和两步回复占下发配额：入口只在剩余额度大于 `reserve_for_final + 1` 时下发，否则不发并上报。
- 等待 `ask_user` 回答的停放状态不算运行中，用户回复正常处理。

启动前确认：
- 长任务启动前，对话 agent 自行判断是否需要向用户确认。只有任务既耗资源又含糊时才问；需求明确就直接启动，回一句"收到"。
- 问什么、问几个由模型根据对话缺失的信息决定，不设固定字段、不设必填项、不做枚举。典型事项：公司名对应多个主体时选哪个、用哪几份上传材料、深度与输出形式、预计耗时与费用量级。
- 这就是 `ask_user` 的一次使用，不需要额外机制。

运行期间：
- 长任务运行期间不向用户提问（MVP）。遇到歧义选最可能的候选，在报告里列出"本次采用的假设"；无法继续则失败并说明原因。
- 以后某个渠道支持中途提问，只需在渠道能力描述里打开开关，核心不用改。

### 7.10 模型调用层的失败处理
分工：
- **调用层**处理不改变请求内容的失败：重试、退避、切备选、熔断、超时、记账。
- **循环**处理必须改请求内容的失败：上下文溢出（要压缩）、输出被截断。
- 调用层把失败分类后返回，循环决定下一步。

分类与处理：

| 类别 | 处理 |
|---|---|
| 瞬时错误：429、5xx、超时、连接重置、usage 缺失或自相矛盾的应答 | 同一模型指数退避加抖动重试，尊重 `Retry-After`，有次数上限 |
| 额度耗尽 | 不重试，切备选并告警。各厂商的错误码清单放配置，代码里不出现厂商分支 |
| 持续不可用（熔断开启） | 切备选，熔断为进程级 |
| 上下文溢出 | 调用层返回分类错误；循环压缩后重试 1 次；仍溢出则以错误码失败 |
| 输出被截断（`length`） | 含工具调用的整批不执行，返回错误让模型重发；纯文本按"达到上限"结束，不续写 |
| 鉴权失败、缺 key | 配置错误，立即失败，不切备选 |
| 工具参数不合法、空响应 | 不归调用层。参数不合法返回错误给模型 |

规则：
- 失败或中断的尝试：已输出的部分丢弃，整次重来，不让模型续写。日志里记录这次尝试和已消耗的 token，不进入模型可见的历史。
- 长报告不靠一次生成完整内容，而是通过写入工具分章节逐段产出，每段单独校验，避免撞输出上限。
- 切备选只因可用性失败，语义失败不切。切换时丢弃上一个厂商的思考回放状态，只保留与厂商无关的消息。每次调用实际用了哪个模型要记进日志，备选的输出质量没有基线，需要可追溯。
- 每次尝试（含失败的）都单独记账，带用途标签、模型、第几次尝试。预算在调用前预扣。
- 全进程同时在途的模型请求数有上限（所有租户共用一个厂商额度），满了排队，排队超时抛 `E5007`（可重试）：请求没有发出，预扣释放，熔断器不计失败。
- 全部数值放配置，初值：瞬时错误重试 3 次，退避约 1 秒、2 秒、4 秒加抖动，溢出压缩后重试 1 次，单次尝试总超时 300 秒。调用为非流式，没有流空闲超时。跑起来再调。
- 预算在预扣的同一条 INSERT 里检查（已结算加未结的预扣加本笔不得超过租户当天的预算，东八区 0 点重置），不是先查后写。
- 预扣悬空（进程在预扣与结算之间崩溃）由 `session/sweeper` 定时释放，阈值在 `configs/session.yaml`。
- 对应的错误码在集中定义处新增，不在别处就地定义。

### 7.11 运行日志
- 运行日志给开发和排障看进程里发生了什么，不是 transcript：transcript 是审计和计费的事实来源，运行日志可丢、不入库。
- 一个汇聚点：`Writer.append` 每写一条 transcript 事件，`session/trace.py` 按事件类型打一行摘要（每个 `EventType` 必须有对应方法，测试守住）。transcript 里没有的事（渠道收发、沙箱、清扫器、模型重试与熔断）在各层显式打。
- 上下文（租户、会话、消息 ID）用 contextvars 带入每行；`loop/scheduler.py` 把上下文复制进线程池。
- 终端中文单行；文件 `logs/<入口>.log`，JSON Lines，按天切分，保留天数走 `configs/logging.yaml`。`console` 渠道只写文件，不和对话界面混在一起。
- INFO 以上不记正文，只记长度和 ID；`preview_chars` 大于 0 才附截断预览，仅限本机调试。
- 运行日志不代替抛错：出错照常抛错误码，日志只是附带记一笔。日志目录不可写，启动时抛 `CONFIG_INVALID`；运行中写文件失败按标准库行为只打印到 stderr，不影响业务。

### 7.12 可观测与评测工具
- 不接 Langfuse 这类外部平台，自己做只含我们关键信息的观测。重新评估的条件：多人要同时看、评测集已经有并且需要横向对比、能确认租户数据不出内网。
- **模型调用记录**：`ModelClient` 每次模型尝试（含失败的）把请求元数据、原始回复和完整思考写进对象存储，键为 `diag/calls/t/<tenant_id>/<session_id>/<调用号:尝试号>.json`。
  - `turn` 只记元数据，messages 可由 transcript 经 `view.derive` 还原；`tool_call`、`compaction` 记完整 messages，图片字节去掉。
  - system prompt 和 tools 的 JSON 按 sha256 存 `diag/blobs/t/<tenant_id>/<sha>`，记录里只存哈希和 `code_version`（git 短哈希，有未提交改动带 `+dirty`），提示词改动由此可追溯到版本。不另建提示词管理平台。
  - 开关 `model.yaml` 的 `call_record`。先结算账本再写记录；写记录失败抛存储错误，不静默跳过，因为有洞的记录会误导排障。记录含租户私有数据，只用于排障。
  - ASR、联网搜索、企业数据查询等不经 `ModelClient` 的计费调用没有调用记录，只在账本里。
- **开发工具在 `devtools/`，可整体拆卸**：`eva/` 不 import 它（pytest 守住），它通过装配层和存储层的读接口取数。
  - `devtools/replay`：把 transcript、账本和调用记录合成结构化时间线，再由渲染端显示，终端和网页共用时间线。transcript 的模型回复事件按时间和账本里的 `turn` 结算对上；对不上的单独列出并标明，不隐藏。
  - `devtools/eval`：案例是一个目录（`case.yaml` 加样本，样本不进 git），`run_case` 走和终端渠道相同的 `Conversation`，不 mock 模型、不开评测旁路。每次运行写 `result.json`（步数、按账本汇总的费用、断言结果、每一轮、标签、代码版本）；`compare` 只读 `result.json`，按标签对比两组。会真调模型，产生费用。
  - 评测租户的 realm 固定是 `eval`，渠道用户 ID 是 `eval_<名字>`，调用方给不出完整租户 ID，指不到真实租户。同一名字解析到同一个租户，同一租户内相同内容的文件复用解析和转写缓存：对比提示词改动时两组用同一个租户名，要重新转写就换名字。
  - 评测集（第 6 节）的题目和 rubric 由用户定；这里是跑批和对比的工具，不预建题目。
- **EVA测评系统**：网页端，列会话、看回放、跑评测、对比结果，只给开发者用，放在 `devtools/`。它读写的都走同样的核心函数，不另写一套。
  - 列出所有租户的会话要跨租户读。存储层单独开一个只读入口：类名带 `Developer`（`eva/storage/developer.py`），只有读方法、没有写方法，是租户过滤的唯一例外，只被 `devtools/` 引用，`eva/` 业务代码引用它由 pytest 拦下。
  - 读不分用途：真实用户（`usr_`）、模拟器（`sim_`）、终端（`dev_`）、评测（`eval_`）的租户都能只读查看会话和回放，方便排查。写只落在评测租户上：评测运行经 `Identities(eval)` 解析租户，人工标注和认可版本的存储层入口拒绝非 `eval_` 租户。
  - 网页只在内网使用，必须登录（单个共享密码，见 `devtools/web/config.yaml`）；它能读到所有租户的私有数据，不对外开放。
  - 运行评测是长任务，网页需要后台任务运行器和进度查询；`run_case` 已带进度回调和取消事件。

新代码全部在 `eva/`，目录名 = 功能层：

```text

  contracts/              跨层共用的约定：errors.py（全部错误码，唯一定义处）、vocab.py（取值集合）、channel.py（渠道与核心交换的 Reply）。只依赖标准库

  session/                会话与运行：单写入者（SessionRunner/Writer）、追加序号、崩溃后补合成结果、悬空预扣清扫（sweeper）；租约与冷恢复后置
  loop/                   agent 循环：turn/step、模型视图（view）、压缩（compaction）、工具批调度（scheduler，线程池，循环内仅此处用线程；渠道的按租户并行在 channels/wecom/lanes.py）、收尾门禁
  tools/                  工具实现与注册：领域工具、read_file、run_python、write_file、deliver_file、web_search、resolve_entity
  hooks/                  hook：租户校验、预算预扣、出处校验，声明式
  sandbox/                执行器接口、local 与 docker 两个后端、宿主侧产物校验、会话工作目录与回收
  channels/               wecom/（crypto 验签解密、client 接口客户端、callback 回调、worker 拉取与处理、lanes 按租户分道的执行器、ports 依赖的形状、config）+ console/。唯一出现渠道数字的地方
  skills/                 skill 加载器与校验（loader.py）；skill 内容在项目根目录 skills/<名字>/（SKILL.md + scripts/）
```

开发用的工具在项目根目录 `devtools/`（`replay/` 会话回放、`eval/` 评测），不属于 `eva/`，可整体删除而不影响运行；只读排障或评测用，见 7.12。

依赖方向，只能向下：

- `contracts`、`common` 最底，不 import 任何其他 `eva` 模块（`contracts` 内部互相引用除外），所有层都可以 import 它们。
- `storage`、`model`、`sandbox` 在底层，不依赖其他内层模块。
- `session` → `storage`；`tools` → `contracts`、`storage`、`sandbox`（将来加 `model`）；`hooks` → `contracts`、`storage`。
- `loop` → `model`、`tools`、`hooks`、`session`。
- `channels` 只 import `contracts`、`common` 和自己渠道的包，不得 import 其他层。它通过装配层给的回调提交用户消息、取得 `Reply`，取消用 `threading.Event` 传入。企微依赖的 Redis 状态和核心入口，渠道只认 `wecom/ports.py` 里的方法形状，实现由 `app.py` 装配（存储层的 `RedisState`、装配层的 `Hub`）。
- `devtools/` 可以 import `eva` 各层的公开接口；`eva/` 里任何文件不得 import `devtools`，由 pytest 守住。
- Redis、SQL Server、MinIO 的客户端库只能在 `storage/` 出现，由 pytest 守住。
- 依赖方向由一个 pytest 测试守住（检查 import 边界），不引额外工具。

原则：

- 不为领域开顶层目录。ASR 热词脚本在 tools，"这家公司指谁"是 skill，报告模板是 skill；领域逻辑落在对应层，不开 `asr/`、`report/` 这类包。
- 可拆卸验证：`channels/console/` 从第一天就有，删掉 `channels/wecom/` 后 `loop` 及以下的测试照常跑通。
- 配置统一进 `configs/`（`model.yaml`、`loop.yaml`、`session.yaml`、`wecom.yaml`、`sandbox.yaml` 等）；阈值、预算、沙箱、渠道参数不硬编码。
