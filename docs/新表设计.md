# 新表设计（eva_perf）

SQL Server 同实例新建库 `eva_perf`，旧 `ccm` 原地只读，作迁移源。旧库形状见 `旧库盘点.md`。目前十九张表；飞轮种子的表（事实、来源、文档原件）暂不建，飞轮设计时定。

## 规矩

- 表变更走迁移脚本（`eva/storage/migrations/NNNN_名字.sql`，执行器 `eva/storage/migrate.py`），不手工改库。已执行的脚本不得再改，改表就新增脚本；执行记录在 `schema_migrations` 表，它是迁移簿记，不算下面的十八张业务表。
- 租户过滤在存储层 API 强制：按租户划分的读写 API 必须带 tenant_id 并过滤，调用方给不出租户就查不了。
- kind、状态、事件类型、渠道标识的取值集合集中定义一处（与错误码同规矩），表里存字符串，不加 CHECK 约束，校验在存储层 API：取值不在集合里就拒绝写入。
- 业务主键用 ULID（varchar(40)，26 位字符的有序唯一 ID，由程序生成）。例外：`tenant_id` 是 `<realm>_<小写 ULID>`（varchar(64)），见 tenants。另一个例外：只追加、没有外部引用、人要靠先后顺序排查的表（如 `channel_messages`、`tenant_memories`），主键用自增的 `seq bigint IDENTITY`：编号短、人工好读，落库先后本身就是顺序，不需要再找排序键。
- 时间一律东八区（UTC+8）：所有时间列是 `datetime2`，存东八区本地时间，不带偏移。代码里只有一个取当前时间的函数，其他地方不得直接调 `datetime.now()`；表上不设 `SYSDATETIME()` 一类的默认值（它取决于服务器时区），时间由应用层传入。企微回调里的 Unix 时间戳也经这个函数转成东八区。
- `tenant_id` 列（及所有引用它的列）和 `tenant_identities.external_id` 的排序规则统一为区分大小写的 `Latin1_General_100_BIN2`。SQL Server 默认规则不区分大小写，只差大小写的两个渠道用户 ID 会被当成同一个人，这是"查到别人的"。

## 几个贯穿全库的概念

- **租户**：一个外部联系人（企微下是客服号加联系人）就是一个租户，一人一份私有数据（架构设计第 6 节）。租户编号由系统生成，渠道里的身份另存 `tenant_identities`。
- **会话**：一段连续对话的容器，对应一份 transcript。企微里每个租户只有一个常驻会话，永不关闭。租户已含客服号，同一用户在不同客服号下是两个租户，会话互相隔离。
- **transcript**：会话里发生的每件事按顺序追加成一行行事件，只增不改，是对话、任务进度、审计、计费回放的唯一事实来源。模型看到的上下文是从它算出来的视图，不单独存。
- **公共层 / 私有层**：公共层是所有租户共享的数据（公司主数据、公共别名、热词），私有层带 tenant_id。租户私有数据不得进公共层（CLAUDE.md 功能权限隔离第 5 条）。

## 表

### tenants

租户，一个外部联系人一行。用户第一次发消息时由 `Identities.resolve` 自动建，没有状态列。

| 列 | 类型 | 说明 |
|---|---|---|
| tenant_id | varchar(64) PK | `<realm>_<小写 ULID>`，系统生成，不含渠道信息。realm 是租户的用途（`usr` 真实用户、`sim` 模拟器、`eval` 评测、`dev` 本地终端），取值集合集中定义。小写，所以也直接拼对象存储路径 |
| created_at | datetime2 | 第一次见到这个用户的时间 |
| skills_rev | int | 租户层 skill 的修订号，初值 0，`tenant_skill_versions` 每写入一行就加一。对话每个 turn 开头读它，变了才重取这个租户的 skill |

没有 minio_bucket、qdrant_ready 这类基础设施映射列。

### tenant_identities

渠道里的"这个人是谁"，指向租户。一个租户可以有多个身份（企微加网页），合并账号就是往这张表加一行。

| 列 | 类型 | 说明 |
|---|---|---|
| realm | varchar(8) | 和 tenant_id 的前缀一致。`Identities` 构造时固定 realm，读写不了别的 realm 的行 |
| channel | varchar(16) | 身份来自哪个渠道：wecom / console / 将来的 web。取值集合集中定义 |
| scope | varchar(64) | 渠道内的范围。企微是客服号（同一用户在不同客服号下是两个身份，各自一个租户）；其他渠道为空串 |
| external_id | varchar(128) | 渠道给的用户 ID 原值。企微是 `external_userid`；模拟器、评测、终端的 ID 带 `<realm>_` 前缀（如 `sim_alice`），只用于辨认和挡住手写的越界输入 |
| tenant_id | varchar(64) FK→tenants | 指向的租户 |
| created_at | datetime2 | |

主键 `(realm, channel, scope, external_id)`，索引 `(tenant_id)`。外部 ID 区分大小写（`Latin1_General_100_BIN2`）。

### sessions

会话。企微里一个租户一个常驻会话，永续不关闭，不按空闲时间轮换，用户随时回来（48 小时窗口只限制我们能不能发消息，不是会话边界）。用户说"新话题"不新建会话，只是在 transcript 里写一个重置事件，让上下文视图从那里重新开始。长任务的子会话也是一行。

"一个常驻会话"是企微适配器的策略，表不做唯一限制：将来网页端要做豆包式的会话列表，直接多建几行。

| 列 | 类型 | 说明 |
|---|---|---|
| session_id | varchar(40) PK | |
| tenant_id | varchar(64) FK→tenants | 会话属于谁 |
| channel | varchar(16) | 会话所在渠道，子会话复制父的值 |
| parent_session_id | varchar(40) NULL | 长任务子会话指向启动它的父会话，普通会话为空 |
| created_at | datetime2 | |

索引 `(tenant_id, channel)`。会话运行中、停放、完成、失败这些状态不存列，从 transcript 推导。

### transcript_events

会话日志。每个事件一行，只追加，没有 UPDATE 和 DELETE。压缩、崩溃恢复、审计、回放、计费核对都读它。

设计思路来自 deepseek-harness 的会话日志（见 `参考-harness源码.md` 第二、十一节）：事件有明确的开始和结束边界，崩溃后才能知道哪一步做到一半；追加时校验序号，两个 worker 同时写也不会写乱。

| 列 | 类型 | 说明 |
|---|---|---|
| session_id | varchar(40) | 属于哪个会话 |
| seq | int | 事件在该会话内的序号，从 0 开始连续递增。追加时调用方必须带"期望序号"，等于当前下一个序号才写入，否则拒绝。这是防止两个 worker 同时写乱日志的兜底 |
| tenant_id | varchar(64) | 冗余存一份，租户过滤不用 join sessions |
| event_type | varchar(32) | 事件类型。取值是基础设施的词汇，不是业务事件：回合开始/结束、用户消息、模型回复、工具调用、工具结果、压缩开始/结束、hook、子 agent 开始/结束、上下文重置、错误等。新增业务能力是加工具，产出的还是工具调用和工具结果，不需要新类型。词表以代码里的集中定义为准，文档不重复 |
| payload | nvarchar(max) | JSON，事件的全部内容，格式随 event_type 而定，可自由扩展，不需要改表 |
| created_at | datetime2 | |

主键 `(session_id, seq)`，聚簇，所以"读某会话从序号 N 开始的事件"是一次范围扫描。索引 `(tenant_id)`。

上下文视图的算法：取最近一次压缩结束事件里的摘要，加上它的切点之后的事件。压缩结束事件的 payload 记切点序号，读取时直接从该序号起扫，不读全表。大工具输出的完整内容不放在 payload 里，放对象存储，payload 只记对象键和预览（架构设计第 7 节）。

### ledger_events

账本，只追加。余额和已用额由事件累加得出，账户上不存状态字段。

记账分三步，对应三种事件（`kind`）：

- **hold（预扣）**：调用模型之前，按预估的最大花费先从预算里占住一笔，这样并发的几次调用不会一起超支。
- **settle（结算）**：调用结束后，按实际用量记账。一次预扣最终对应一条结算。
- **release（释放）**：调用失败、被取消或 worker 崩溃时，把占住的额度还回去。一次预扣要么结算要么释放，二选一。

已用额 = 所有 settle 的 amount_cny 之和；占用额 = 还没有 settle 也没有 release 的 hold 之和；可用额 = 预算 − 已用额 − 占用额。

预算按租户、按东八区自然日计：只统计创建时间在当天 0 点之后的行，租户的所有会话合计，次日 0 点重置。同一用户在两个客服号下是两个租户，各有一份额度。跨零点还没结算的预扣记在前一天，它的结算行记在结算那天，所以那次在途调用结算前不占今天的额度。超额抛 E4004，详情带 `resets_at`（下次 0 点），渠道据此告知用户。

| 列 | 类型 | 说明 |
|---|---|---|
| event_id | bigint identity PK | 自增序号，只用来排序 |
| tenant_id | varchar(64) | 花的是谁的钱 |
| session_id | varchar(40) | 在哪个会话里花的，子会话的花费记在子会话上 |
| kind | varchar(8) | hold / settle / release |
| hold_id | varchar(40) | 同一次预扣的 hold、settle、release 共用同一个值，用来把它们串起来 |
| idem_key | varchar(64) | 幂等键，取模型调用 ID。`(idem_key, kind)` 唯一：同一次调用的同一类事件重复写（比如重试、崩溃后重放）会被直接拒绝，不会记两次账 |
| purpose | varchar(32) | 这笔钱花在哪：对话回合、压缩、工具内调用、ASR 等，取值集中定义，用来分开统计 |
| model | varchar(64) NULL | 调用的模型名；ASR 按秒计费没有模型，为空 |
| amount_cny | decimal(10,4) | 金额，单位元。hold 是预估上限，settle 是实际花费，release 是还回的额度 |
| tokens_in / tokens_out | int NULL | 输入、输出的 token 数，只在 settle 上填 |
| cache_hit_tokens / cache_miss_tokens | int NULL | 输入 token 中命中、未命中缓存的数量，命中的单价更低，只在 settle 上填 |
| asr_seconds | int NULL | ASR 识别的音频秒数，只在 settle 上填 |
| pricing_version | varchar(32) | 算 amount_cny 用的是哪一版价目表。模型调价后，历史账单仍能解释当时为什么是这个金额 |
| created_at | datetime2 | |

索引 `(hold_id)`、`(tenant_id)`、`(session_id)`、`(tenant_id, created_at)`（预扣时对当天的行求和并加范围锁）。worker 崩溃留下"有预扣无结算"，由定时清扫判运行租约过期后补一条 release。

### file_registry

文件登记表：用户传的文件存在哪、解析过没有。状态之间没有转换规则，直接覆盖写（架构设计第 3 节资源类记录）。

| 列 | 类型 | 说明 |
|---|---|---|
| file_id | varchar(40) PK | |
| tenant_id | varchar(64) | 文件属于谁 |
| sha256 | char(64) | 文件内容的哈希。同样内容哈希相同，是解析缓存键的一半 |
| filename | nvarchar(512) | 登记后的文件名。同一租户内未删除的文件不重名：别的内容已占用时改成"名字(2).扩展名"，引用靠它定位唯一一份 |
| mime | varchar(96) | 文件类型 |
| bytes | bigint | 文件大小 |
| minio_key | nvarchar(512) | 原件在对象存储里的完整对象键 |
| parsed_key | nvarchar(512) NULL | 解析结果缓存的对象键。非空表示已经解析过，再次读取直接命中，不重复解析 |
| status | varchar(16) | uploaded（已收到，尚未可用）/ available（可用）/ deleted（已删除） |
| created_at | datetime2 | |

唯一索引 `(tenant_id, filename) WHERE status <> 'deleted'`：同一租户内未删除的文件不重名，登记时先改名，并发撞名时由索引拒绝、登记重试换名。
唯一约束 `(tenant_id, sha256)`：同一租户同样内容只有一行，重传时更新原行、对象存储里覆盖。不同租户传同一份文件互不影响，也不共享缓存，否则命中缓存会暴露别的租户传过这份文件。

### file_deliveries

文件交付给用户的记录，只追加。同一份文件可以在不同会话反复交付，每次一行。列"以前交付过的文件"（历史报告）靠它，不靠文件名猜。

| 列 | 类型 | 说明 |
|---|---|---|
| delivery_id | varchar(40) PK | |
| tenant_id | varchar(64) | |
| file_id | varchar(40) | 外键到 `file_registry`。写入时和租户一起校验，别的租户的文件登记不进来 |
| session_id | varchar(40) | 在哪个会话交付的。不加外键，只是出处 |
| scenario | varchar(64) NULL | 报告声明的场景（如尽调）。取自报告里嵌的引用清单，没有清单的文件（转写稿等）为空 |
| uscc | char(18) NULL | 报告声明的公司信用代码，同上 |
| delivered_at | datetime2 | 登记交付的时间。登记发生在 `deliver_file` 调用时，渠道真正发出在回合结束，可能因窗口或配额没发出去，所以它表示"系统交付过"，不保证用户收到 |

索引 `(tenant_id, delivered_at DESC)`、`(file_id)`。`list_files` 查本租户有交付记录且可用的文件，每份取最近一次交付的场景和信用代码，按最近交付时间倒序。

### channel_messages

渠道实际收到、发出的每条消息，只追加。**不是主流程需要的**：agent 核心、工具和模型都不读它，删掉这张表主流程照常运行。它只用来重建对话（模拟器重启或换机器后还原页面）和开发排障。

transcript 是模型视角的记录，`file_deliveries` 只表示"系统登记了交付"，二者都不能证明渠道真的收发了什么：企微有窗口和条数配额，登记了的文件可能被暂存、被合并成文件、被拒。这张表补的就是这个缺口：只记真正发出和收到的，暂存的等补发成功时才记。

只由渠道适配器写（企微 worker 收到消息时记入站，`send_text`、`send_file`、`send_menu` 成功后记出站），列保持渠道无关，不放窗口、配额这类渠道数字。记失败时消息已经收发，不能回滚也不能重试（重试会重复发），只上报，不影响收发。

| 列 | 类型 | 说明 |
|---|---|---|
| seq | bigint IDENTITY PK | 落库先后，也是对话顺序。同一租户同一时间只有一条消息在处理，落库顺序就是对话顺序；时间列在 Windows 上分辨率不够，不能当排序键。这是不用 ULID 的例外：只追加、没有外部引用，只需要先后 |
| tenant_id | varchar(64) FK→tenants | |
| direction | varchar(8) | `in`（用户发来）或 `out`（发给用户） |
| msg_id | varchar(128) | 入站是渠道的消息 ID，出站是发送时给渠道的消息 ID（同一条回复重发时相同） |
| kind | varchar(16) | `text`、`file`、`image`、`voice` |
| text | nvarchar(max) NULL | 文本内容。以文字发出的短文件记成文本；长回复转成的 md 文件没有登记，全文记在这里 |
| file_id | varchar(40) NULL FK→file_registry | 内容在文件登记里。超限被拒的文件和语音、长回复转成的 md 没有。写入时和租户一起校验，别的租户的文件进不来 |
| filename | nvarchar(512) NULL | 用户看到的文件名 |
| bytes | bigint NULL | |
| created_at | datetime2 | 入站取渠道的发送时间，出站取发出时刻 |

唯一约束 `(tenant_id, direction, msg_id)`：重复投递、重发时不产生第二行，写入按"已记过"处理。索引 `(tenant_id, seq)`。

不加 `session_id`：入站消息到渠道时核心还没选出会话，渠道拿不到；用户看到的是跨会话的一条连续聊天，按租户和先后重建就对。排障要对应到会话，用时间去对 `transcript_events`。网页端以后做会话列表时，再给这张表加一个可空的 `session_id`，由网页适配器填（它自己知道会话），不在现在预留。

### tenant_memories

租户记忆：用户明确要求记住的偏好和纠正（"以后报告用简体""不要加免责声明"），只属于这个租户，不进公共层。只追加，主键用自增 `seq`：记一条是一行 `op=add`，忘掉是另写一行 `op=forget`，用 `target_seq` 指向被忘掉的那条 add。生效的是没有被 forget 指向的 add；行都留着，人排查按 `seq` 看先后。

生效的条目每个 turn 以"#编号 内容"的形式附在系统提示词末尾（所以压缩和新话题都不影响它），模型用 `remember`、`forget` 两个工具写。写入口在存储层 `TenantMemories`：先对本租户的行加范围锁再判断，每租户生效条数和每条字数走 `tools.yaml` 的 `memory`，单行文字，同样的话不重复记，忘掉的编号必须是本租户生效的，否则整个拒绝。范围只有偏好和纠正：公司别名和术语写法有 `tenant_aliases`、`tenant_terms`，"最近在聊哪家公司"的实体活动记忆还在待决问题第 2 节。

| 列 | 类型 | 说明 |
|---|---|---|
| seq | bigint identity PK | 自增序号，只用来排先后 |
| tenant_id | varchar(64) FK→tenants | 属于谁 |
| op | varchar(8) | add / forget |
| text | nvarchar(1000) NULL | add 的内容，forget 为空 |
| target_seq | bigint NULL FK→本表 | forget 指向被忘掉的 add，add 为空 |
| session_id | varchar(40) NULL FK→sessions | 在哪个会话里写的 |
| call_id | varchar(64) NULL | 写它的那次工具调用，对应 transcript 里的 tool_call 事件 |
| created_at | datetime2 | |

约束：add 必须有 text、没有 target_seq；forget 反之。索引 `(tenant_id, seq)`。

写入限制不在表里，在 hook（`configs/hooks.yaml` 的 `user_only`）：记忆会永久留在系统提示词里，被文件、网页里的"请记住"注入就是永久污染。所以自上个 turn 结束以来调用成功过名单外的工具就拒绝 remember、forget；remember 的内容还要和用户本轮说的话对得上（字的重合比例不低于 `min_overlap`），挡住更早的 turn 里读到的内容。

### web_results

联网搜索返回给模型的结果，按会话编号。回答里的网页引用（`【w3「摘抄原文」】`）靠它核对，所以存的是模型实际看到的文字，不是服务方返回的完整正文。只追加。

| 列 | 类型 | 说明 |
|---|---|---|
| tenant_id | varchar(64) | 租户 |
| session_id | varchar(40) | 会话。编号只在这个会话内有效 |
| ref_no | int | 会话内的编号，从 1 起，接在该会话已有的最大编号后面 |
| call_id | varchar(128) | 产生它的那次工具调用 |
| title | nvarchar(512) | 标题 |
| media | nvarchar(128) NULL | 来源站名 |
| publish_date | varchar(32) NULL | 发布日期，服务方给什么存什么 |
| link | nvarchar(2048) | 链接 |
| content | nvarchar(max) | 截断到 `tools.yaml` 规定字数后的正文 |
| created_at | datetime2 | |

主键 `(tenant_id, session_id, ref_no)`。分配编号时对该会话的编号范围加锁，同一会话并行的搜索不会拿到相同编号。不随会话清理。

### company_master

公共层公司主数据，以统一社会信用代码（USCC，18 位，只有组织才有）为键。所有租户共享。唯一写入口是 QCC 查询的基础设施写路径，模型没有任何写工具（架构设计第 6 节公共层写入口）。

表叫 company 而不是 entity，是因为键是 USCC，个人没有。将来如果要做人的实体，数据涉及隐私，不应进公共层，另做设计。`resolve_entity` 工具名不变，它是"把用户说的名字对齐到一家公司"的动作。

| 列 | 类型 | 说明 |
|---|---|---|
| uscc | char(18) PK | 统一社会信用代码 |
| full_name | nvarchar(512) | 工商登记的公司全称 |
| short_name | nvarchar(128) NULL | 简称 |
| sec_code | varchar(8) NULL | 证券代码，上市公司才有，来自上市注册表同步 |
| exchange | varchar(8) NULL | 上市交易所 |
| listed_at / delisted_at | date NULL | 上市日期 / 退市日期 |
| data_json | nvarchar(max) NULL | QCC 查询的完整返回。旧数据迁移时为空，首次被查询时回填 |
| fetched_at | datetime2 | 上次从 QCC 取数的时间，超过配置的有效期就重新查 |
| updated_at | datetime2 | 这一行上次被写入的时间。和 fetched_at 分开，是因为注册表同步只改上市相关字段，不代表重新取过 QCC 的数 |

### company_aliases

公共别名：一家公司除了 `company_master` 里全称和简称之外的叫法，指向 USCC。包括曾用名、英文名、历史行情里用过的别名等。与主表 `full_name` / `short_name` 文字相同的名字不在这张表里存第二份（派生数据不落表，主表改名时也不会出现两份不一致）。`resolve_entity` 按名字查时同时查这张表和主表的 `full_name`、`short_name`（两列各有索引），命中就不用调 QCC（QCC 要花钱，也有延迟）。来源是旧库迁移、QCC 返回和离线任务。租户自己确认的别名不进这张表。

| 列 | 类型 | 说明 |
|---|---|---|
| alias_id | bigint identity PK | 自增 |
| uscc | char(18) FK→company_master | 这个别名指向哪家公司 |
| alias | nvarchar(512) | 别名文字 |
| alias_kind | varchar(16) | 别名种类，取值沿用旧库：SHORT（简称）/ FULL（全称）/ ENGLISH（英文名）/ FORMER（曾用名）；新增 GROUP（集团或品牌的口语叫法，如"阿里"，指向旗下一家境内主要运营主体，同一个叫法可以指向多家） |
| source | varchar(24) | 这条别名怎么来的：legacy（旧库迁移）/ qcc / offline（离线任务） |
| created_at | datetime2 | |

唯一约束 `(uscc, alias, alias_kind)`，索引 `(alias)`（按名字查）。

### tenant_aliases

租户私有的别名确认：某个用户说的某个称呼，经用户确认就是某家公司，下次 `resolve_entity` 直接命中。只属于这个租户，不进公共层，也不影响别人。

| 列 | 类型 | 说明 |
|---|---|---|
| alias_id | bigint identity PK | 自增 |
| tenant_id | varchar(64) | 谁确认的 |
| alias | nvarchar(512) | 用户的称呼 |
| uscc | char(18) FK→company_master | 确认后对应的公司 |
| session_id | varchar(40) NULL | 在哪个会话里确认的，审计用 |
| created_at | datetime2 | |

唯一约束 `(tenant_id, alias)`：同一个称呼重新确认时覆盖原行。

### tenant_terms

租户私有的已确认写法：用户确认过的公司名、人名、术语的正确写法，以及它常被听成什么。转写纠错时 `search_hotwords` 先查它再查公共热词表。只属于这个租户，不进公共 `asr_hotwords`，也不影响别人。

| 列 | 类型 | 说明 |
|---|---|---|
| tenant_id | varchar(64) | 谁确认的 |
| term | nvarchar(256) | 正确写法 |
| heard_as | nvarchar(256) NULL | 常被听成的错误写法 |
| kind | varchar(16) | company / person / term（取值见 `eva/contracts/vocab.py` 的 `TermKind`） |
| session_id | varchar(40) NULL | 在哪个会话里确认的，审计用 |
| created_at | datetime2 | |

主键 `(tenant_id, term)`：同一个写法重新确认时覆盖原行。每租户条数上限在 `configs/tools.yaml` 的 `confirm_term`。

### tenant_skill_versions

租户层 skill，只追加：每次修改、回退、归档都是新增一行，当前生效的是每个 `(tenant_id, name)` 版本号最大的那行。只属于这个租户，不进公共层，也不影响别人。公共层的 skill 在仓库 `skills/` 下，不在库里。

| 列 | 类型 | 说明 |
|---|---|---|
| tenant_id | varchar(64) FK→tenants | 属于谁 |
| name | varchar(64) | skill 名，命名规则同 `skills/` 下的目录名 |
| version | int | 同一 `(tenant_id, name)` 内从 1 递增 |
| kind | varchar(16) | addendum（补充：叠在同名公共 skill 的正文后面）/ own（租户独有：公共层没有的名字）。取值见 `eva/contracts/vocab.py` 的 `SkillKind` |
| status | varchar(16) | active / archived。归档是新增一行 archived，不删行，可以再追加 active 恢复。取值见 `SkillStatus` |
| description | nvarchar(1024) NULL | 只有 own 填，写进该租户的清单；addendum 为 NULL，清单沿用公共 skill 的 |
| body | nvarchar(max) | addendum 是补充的内容，own 是完整正文。归档的行也保留原文 |
| reason | nvarchar(512) NULL | 为什么改，审计和回退时看 |
| created_at | datetime2 | |

主键 `(tenant_id, name, version)`。

- 写入走存储层唯一的写入口，同一事务里：锁住该租户的 `tenants` 行，取下一个版本号，插入新行，`tenants.skills_rev` 加一。锁租户行同时让同租户的并发写入串行，版本号不会重复。
- 写入口校验：名字合规；`kind=addendum` 要求公共层有这个名字；`kind=own` 要求公共层没有这个名字；正文非空且不超过 `max_body_bytes`；own 的 description 非空且不超过 `max_description_chars`；每租户 active 的 skill 数不超过 `max_tenant_skills`。上限都在 `configs/skills.yaml`。校验不过直接抛错，坏内容进不了库，运行时读取租户层不会遇到不合格的行。
- 只存正文，不存 `references/` 和 `scripts/`：补充通常很短，等哪份补充长到要拆时再加表。脚本永远只在公共层，运行时不可写。
- 公共层后来新增了与某个 own 同名的 skill，或删掉了某个 addendum 对应的 skill：读取时该租户的这一条被忽略，并按 `CONFIG_INVALID` 报一次错，其余照常。租户层不覆盖公共层。
- 回退不是改旧行：追加一行，内容取自要回到的版本。


### qcc_results

| person | nvarchar(128) NULL | 人名，只有需要人名的维度才有 |
| record_no | int | 这条在 QCC 返回名单里的序号（从 1 起） |

### qcc_queries

`query_company` 每次调用的结果留痕，只追加。`qcc_results` 只存有记录的行，"查了但没有"和"没查"在那里分不出来；场景报告（如尽调）交付前按它核对必备维度有没有查过。缓存命中也记一条。

### qcc_cache

公共层的企业数据查询缓存，防止同一家公司的同一维度反复向 QCC 付费。企业公开数据对所有租户相同，所以所有租户共享一份。唯一写入口是 `query_company` 拿到 QCC 返回之后的基础设施写路径，模型没有任何写工具；只写 QCC 确认有数据的结果（包括确认为空的名单），"没匹配上"不写，免得把用户随口说的人名之类的自由文本放进公共层。

## MinIO 布局

单桶 `eva`，不再每租户一个桶。旧系统每租户一桶，要在建租户时先建桶并记映射列；单桶按路径前缀隔离，首条消息不用建桶，也没有映射列，生命周期规则和备份只配一次。代价是隔离靠存储层强制加前缀，而不是桶策略，也不能按租户设配额，目前规模下可以接受。

- `t/{tenant_id}/files/{file_id}`，上传原件。`t` 是 tenant 的缩写，标明租户私有区
- `cache/parsed/t/{tenant_id}/{sha256}/{parser_version}.json`，解析缓存，键是（租户，内容哈希，解析器版本）；`parsed_key` 记最近一次写入的键
- `cache/vision/t/{tenant_id}/{图的sha256}/image.png`，解析时留给视觉模型的图，按内容哈希存，解析缓存的 `images` 记块序号到它的哈希；同目录 `{vision版本}.txt` 是这张图的描述缓存
- `cache/overflow/t/{tenant_id}/{session_id}/{ulid}`，大工具输出溢出产物，对象键记进 transcript，不建登记表

公共层不进 MinIO，公司主数据在 SQL。

生命周期：原件和交付物（`t/{tenant_id}/files/`）不设保留期，不自动删除；评测输入快照（`t/{tenant_id}/eval_inputs/`）被数据库引用，也不过期。会过期的对象放在 `<类别>/` 之下，租户前缀放在类别后面：桶级生命周期规则只能按固定前缀过期，这样新增租户不用改规则。过期天数按最后写入时间算，在 `configs/storage.yaml` 的 `expire_days`，由 `ObjectStore.apply_lifecycle` 同步到桶（只动 ID 以 `eva-expire-` 开头的规则，别的规则保留）：

| 前缀 | 天数 | 说明 |
|---|---|---|
| `cache/overflow/` | 30 | 大工具输出溢出，只在所属会话内读取 |
| `cache/parsed/` | 90 | 解析缓存，过期后读取按"没有缓存"重新解析 |
| `cache/vision/` | 120 | 看图描述和图，必须比 `cache/parsed/` 长：解析缓存记着图的哈希，图先过期会读不到 |
| `diag/calls/` | 30 | 模型调用记录，只用于排障，含租户私有数据 |
| `diag/blobs/` | 60 | 调用记录引用的提示词和工具定义，必须比 `diag/calls/` 长，回放才找得到 |

键里写成 `cache/parsed/t/{tenant_id}/…`。同样内容重复写入的对象每次写都会续命。配置加载时会检查"被引用的比引用它的长"，规则已同步到服务器上的桶 `eva`。

## 迁移

建表走迁移脚本。数据由一次性脚本 `eva/storage/legacy_import.py` 从 `ccm` 迁入，旧库只发 SELECT，写新库在一个事务里完成。范围见 `旧库盘点.md`，只迁公共数据。

**只补缺，不覆盖已有行**：目标里已有的行跳过。公司主数据上线后会被 QCC 回填 `data_json`，租户别名又引用它，重跑不能抹掉这些。去重键：公司按 uscc，别名按 `(uscc, alias, alias_kind)`，热词按 `(term, source_kind)`。重复执行结果相同。

- companies → company_master。company_id 即 uscc，fetched_at、updated_at 取旧 updated_at，data_json 置空等首次查询回填。
- company_aliases → company_aliases，alias_kind 原样（SHORT / FULL / ENGLISH / FORMER），source=legacy。FULL 和 SHORT 里与主表同名字段相同的不迁（相同按数据库排序规则判断，忽略大小写和全半角）；不同的保留，例如主表简称是行情里带 XD、*ST 前缀的名字，别名是干净的叫法。旧表没有 created_at，取迁入时间。
- asr_hotwords → asr_hotwords，source_kind 原样（LISTED_COMPANY / INDUSTRY_TERM）。
- listed_company_registry 不写入任何表，只用来对账。按 sec_code 加 exchange 匹配 companies：匹配上的核对上市日期和上市状态是否一致，不一致的计入摘要；匹配不上的是没有 uscc 的上市公司，进不了 company_master，全量写入 `docs/迁移未匹配上市公司.csv` 供人工看，不猜 uscc。

自增 id（alias_id、hotword_id）不沿用旧值。旧库的时间列本身就是东八区，原样写入，不做转换。uscc 落 char(18)，旧值不是 18 位的，以及指向这类公司的别名，进异常清单，不写入。alias_kind、source_kind 出现集合外的值就整体拒绝。

对账：通过校验的每一行源数据，目标里都必须存在，否则抛 E9004 并回滚。摘要输出每张表的通过校验行数、新插入行数、目标已有行数、异常行和注册表对账结果。
